## Подтверждённые свойства

Сервер: `https://ord-prestable.yandex.net`. Методы имеют префикс `/api/v8/`; `info.version=0.0.2` — метаданные спецификации, не версия пути API. Авторизация описана схемой HTTP Bearer (OAuth). Спецификация доступна без токена; это не подтверждает доступ к самим методам.

Время жизни загруженных объектов тестового стенда — **1 месяц**.

Восемь путей: `organization`, `contract`, `platforms`, `creative`, `statistics`, `invoice`, `invoice/creatives`, `status`. Схемы запросов и ответов следует читать непосредственно в JSON.

Для проверки обработки используется `GET /api/v8/status?reqid=…`. Для организации, договора, креатива и акта есть GET по `object_id`. DELETE-методы в снимке не описаны.

Наличие токена маркировки в ответе не гарантирует регистрацию креатива в ЕРИР: описание `ResponseStatus.token` требует `ERIR async success`. Для массовых запросов есть `object_statuses`. Ответ `/status` содержит не более 100 сообщений об ошибках.

## Доступ и ограничения выводов

По инструкции подключения главный представитель или администратор выдаёт API-доступ пользователю кабинета; персональный токен связан с его Яндекс ID. Один пользователь может иметь API-доступ только к одному кабинету.

Отдельная процедура выдачи sandbox-токена в прочитанной инструкции не описана. Нельзя считать доказанными ни обязательность отдельного токена, ни работоспособность production-токена в sandbox без проверки.

`PlatformType` допускает `site`, `apps`, `smarttv`, `hbbtv`; тип для канала MAX этими значениями не определяется. Правила передачи тестовых данных в ЕРИР, применимость тестового erid и согласованные параметры агентской цепочки остаются неподтверждёнными.

Снимок позволяет сверять адаптер с документированным контрактом без доступа к API. Он не заменяет живой прогон и не закрывает вопросы плана [проверок ОРД](../plans/feature-checks-ord.md).

## Обновление

При повторной загрузке сохранить новый датированный JSON и обновить эту справку с датой и SHA-256. Старый снимок сохранять для сравнения изменений контракта. Токены и реальные ответы с персональными данными сюда не добавлять.

### Проверка длительного ожидания — 2026-11-07

Обнаружена и исправлена лишняя блокировка диагностического сценария: готовность ссылки на организацию/договор/площадку была объединена с окончательным успехом ЕРИР. Contract.clientId и contractorId в свежей OpenAPI требуют регистрации организации в ОРД. SHA256 повторно скачанной спецификации совпал с сохранённым снимком.

Теперь dependency_ready разрешает ссылки на организации, договоры и площадки после ERIR sync success (при отсутствии промежуточных/ошибочных дочерних статусов). Это не переводит шаг в done: его квитанция продолжает опрашиваться, а полная цепочка не объявляется завершённой. Для креатива и отчётности правило не ослаблено. В логах квитанция названа ord_request_id, чтобы не конфликтовать с request_id корреляции CLI.

Живая проверка подтвердила переход: при sync-статусах контрагентов оба договора и площадка приняты и достигли ERIR sync success. Креатив сначала отклонён HTTP 422 до выдачи квитанции: для ККТУ 30.15.1 требуется description. Добавлено описание тестовой услуги; сохранена копия отклонённого состояния, исправленный запрос принят и достиг ERIR sync success. Создано семь объектов, пять отчётных шагов ещё не отправлены.

Текущее ожидание относится к финальной регистрации креатива: ResponseStatus.token явно требует ERIR async success даже при наличии erid. Опрос GET /api/v8/status с параметром reqid соответствует спецификации, ответ сверяется с сохранённой квитанцией. Срок асинхронной обработки и причина задержки не подтверждены; необходимость входящего webhook не установлена и для используемого polling-сценария он не нужен. Нельзя объявлять sync окончательным успехом ради завершения теста.

Тесты TestORDSandbox* и TestIntegrationCheckORD*, адресный go vet и сборка проходят. Добавлены регрессии разделения готовности ссылки и окончательного успеха, дочерней ошибки и запрета отчётности при одном лишь sync/erid креатива.
