# Notification detail links must match the cabinet router

**Date:** 2026-11-17 23:21 +04:00
**Files:** internal/notification/{domain,app,render}, templates/notification, internal/bootstrap/notification_*_test.go, mockapi/internal/{store,seed,api}, api/openapi.yaml, internal/apigen/api.gen.go
**Severity:** medium

## Problem

MAX channel notifications linked to `/blg/channels/{id}` instead of the working `/blg/channel/{id}`. Advertiser orders, blogger placements and administrator detail links had the same mismatch. Several shared notification instructions described obsolete or conditional behavior as unconditional.

## Root Cause

The original notification plan explicitly assumed cabinet routes without verifying the frontend. Tests repeated those assumptions, so they passed while notification links opened missing pages or just the placement list. MAX and Telegram share the same templates and link payload; the defect affected both, email and cabinet history.

## Solution

Verified routes against `maxim-frontend/src/shared/config/routes.ts` and the placement page's route parameter. Generate singular detail routes for channels, placements and orders. Normalize the six legacy link forms when reading notifications, covering cabinet history and pending deliveries without mutating stored payloads or resending delivered messages. Update mock notifications, contract example and generated specifications. Add a debug `[FIX]` planning log with template, role, object and resulting link.

Update shared copy: reconnect a channel from the cabinet instead of sending an obsolete code; contact support after final payout failure instead of promising an automatic retry; use neutral wording for manual/automatic acceptance and returns to preparation; keep provider reason codes out of user-facing contractor-blocked messages.

## Prevention

- Verify cabinet links against frontend routes, not HTTP API paths or list-page names.
- Test every catalog template and allowed role through the production planner and MAX, Telegram, email and cabinet outputs.
- Cover persisted legacy links separately from newly planned notifications.
- Check notification wording against all callers, including system transitions, automatic acceptance and final payout failures.
- Validation passed: domain/render regressions, notification/bootstrap packages (excluding the Docker-only production edge test), the full mock API suite, code generation, targeted `go vet` and `git diff --check`. HTTP suites needed execution outside the sandbox to connect to their own loopback test servers. Docker is unavailable here, so PostgreSQL-backed integration scenarios were skipped and require a Docker-enabled environment.
