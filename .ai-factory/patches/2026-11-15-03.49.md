# Дневной прирост просмотров вместо повторения среднего охвата

**Date:** 2026-11-15 03:49 Europe/Astrakhan
**Files:** internal/channel/{domain,app,postgres,httpapi}, migrations/00110_channel_view_observations.sql, api/openapi.yaml, generated Go/TypeScript contracts, mockapi/internal/{handlers,store,seed,server}; frontend metrics components and LineChart
**Severity:** medium

## Problem

График «Просмотры» рисовал `avg_views`: один пост с пятью накопленными просмотрами
давал линию 5 каждый день. Интерфейс позволял принять её за пять новых просмотров
ежедневно. Новый канал не объяснял, почему настоящей истории динамики ещё нет.

## Root Cause

Модель хранила только средний накопленный охват поста и число подписчиков.
Исходные счётчики отдельных публикаций между проверками не сохранялись.
Изменение среднего или суммы скользящего окна не равно новым просмотрам:
удалённые и вышедшие из окна посты меняют такую сумму сами по себе.
Mock API дополнительно генерировал выдуманную историю при каждом GET канала.

## Solution

Хранить отдельную контрольную точку и счётчики просмотров по MID, атомарно с
суточным снимком под блокировкой канала. Первое чтение создаёт исходную точку
без `new_views`; следующие считают только известный прирост. Повторы в один день
накапливают дельту, не добавляя старые просмотры заново. Неизвестные счётчики,
сброс, усечение и пропущенные дни оставляют неизвестный прирост, а не ноль.
Устаревшие параллельные результаты отбрасываются; дата снимка соответствует
реальному чтению, а не просроченному заданию. Исторические средние не
превращаются в фиктивные дневные просмотры. Хранилище рабочих счётчиков
ограничено читаемым окном; тексты сообщений не сохраняются.

API дополняется необязательными `new_views`, `subscribers_change`, `observed_at` и
`views_period_started_at`. Старый `avg_views` сохраняет смысл среднего по постам
за 30 дней и остаётся основанием ERR/CPV. Дневной прирост подписчиков вычисляется
на сервере из последовательных реальных суточных итогов, включая дополнительную
исходную дату перед окном 30 дней. Это чистый прирост с учётом отписок
(`subscribers_change`), а не валовые подписки. Столбцы новых просмотров и линия
прироста подписчиков совмещены с отдельными шкалами; абсолютное количество
показано мини-графиком справа от сводки 2×2. Пропущенные даты разрывают линию,
ноль и одиночные измерения видимы.
Первый замер показывает текущую сводку и уведомление о сборе истории.
Mock API возвращает только явно сохранённую историю; демонстрационные данные
начальных каналов создаются при seed, а не при чтении нового канала.

Проверено: Go app/domain/httpapi-тесты с настоящим PostgreSQL и `CI=true`,
компиляция всех пакетов и тестовых реализаций `go test ./... -run '^$'`,
`go vet ./internal/channel/...`, `sqlc vet`; mock API server/store/seed-тесты.
Во фронтенде прошло 35 тестов, production build и линтеры затронутых файлов.
Дополнительно проверены суточный знаковый прирост подписчиков и исходный замер
перед окном 30 дней в PostgreSQL, HTTP и mock-контракте. Проверены desktop/mobile,
первое наблюдение, ширина 1024px и подсказка на 320px; скриншоты находятся в
`output/channel-metrics/`. Обе рабочие копии прошли `git diff --check`.
Изменения локальные; деплой и коммит не выполнялись. Tasker недоступен, задача
и отчёт не опубликованы. Действующий SSH-доступ к dev отсутствует.

## Prevention

- Не называть накопленный средний охват просмотрами за день.
- Не вычислять дневной прирост из среднего или суммы движущегося окна.
- Проверять 5 → 5 → 8 как исходный замер → 0 → 3 новых просмотров.
- Различать неизвестную величину и измеренный ноль на всех слоях.
- Проверять повторы, новые/исчезнувшие посты, неполноту, сброс и пропуски;
  отдельно проверять атомарный откат и устаревшие параллельные ответы.
- Даты истории — фактические наблюдения, а не реконструкция до подключения.
- Подписывать область измерения: доступные посты в окне 30 дней, прирост между
  проверками; точное распределение внутри интервала из MAX не восстанавливается.
