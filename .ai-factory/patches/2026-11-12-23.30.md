# RocketWork connection status did not trigger a provider lookup

**Date:** 2026-11-12 23:30 Europe/Astrakhan
**Files:** internal/payout/app/contractors.go, internal/payout/app/executor_identity_test.go; frontend src/features/rocketwork-connect/{api/rocketworkApi.ts,model/rocketworkText.ts,ui/RocketworkCard.tsx}, src/entities/payout/model/status.ts, src/pages/blg-payouts/ui/BlgPayoutsPage.test.tsx
**Severity:** medium

## Problem

Connecting an already registered RocketWork executor displayed "Invitation sent".
The manual status button did not actually ask RocketWork for an updated status.

## Root Cause

The initial invited database state is created before the asynchronous lookup or
invitation. The frontend treated it as evidence of a delivered invitation.
Its refresh button only repeated GET of the cached application state, instead of
POSTing the existing refresh operation. Lookup errors remained invisible until
exhaustion and the cabinet did not interpret them.

## Solution

Use POST /blogger/rocketwork/refresh for manual checks and bounded 30-second GET
polling after connect/check; retain GET-only retries for failed reads. Display
connection requested wording, provider-directed guidance, and explicit check errors.
Do not offer repeated connection requests while awaiting the initial result.
Scoped backend refresh always queues an executor read even before binding; it
does not itself send another invitation. Record sanitized lookup failures and
expose contact_support through the existing next_action field; successful reads
clear the failure. Expected not-found for an unbound executor is not shown as a
lookup failure. Identity checks and payment authorization stay unchanged.

## Prevention

Test asynchronous state separately from external side-effect confirmation. UI
refresh tests must assert the operation that schedules authoritative work, not
just that a GET happened. Verify that existing executors bind without onboarding
writes, lookup failures are visible and recover, and delayed status updates reach
the UI. Tests use isolated PostgreSQL with CI=true to prevent silent skips.

Nine frontend page tests passed; type checking, production build, changed-file
ESLint and related Go integration tests passed. Desktop/mobile component previews
were inspected with synthetic responses. The affected live account and deployment
were not verified because the documented SSH key was unavailable. Tasker tools
were unavailable, so task creation, status updates and the report were not posted.
