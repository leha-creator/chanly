## Контекст исследования

Источник: `.ai-factory/RESEARCH.md`, только относящиеся к задаче пункты `Active Summary` от 2026-10-12; старые ограничения сверять с текущим кодом и официальным API.

- Цель проекта: биржа рекламы в каналах MAX, кабинеты рекламодателя, блогера и администратора.
- Стек: Go + React; MAX Bot API, токен в заголовке `Authorization`, доверенные TLS-сертификаты.
- Ограничения: production получает события через HTTPS Webhook; текст сообщения — до 4000 символов, вложения передаются через API MAX.
- Решение проекта: надёжность через задания, идемпотентность и повторы. Поддержка не меняет правила размещений, ОРД и денег.
- Исходные вопросы исследования о доступах и других интеграциях не являются требованиями этой функции. Поведение конкретного бота и возможность чтения старой истории пока не проверены.

Проверенные точки расширения:

- `internal/channel/httpapi/webhook.go`, `internal/platform/inbound/` — проверка подлинности, атомарная запись события и job, быстрый ответ webhook.
- `internal/channel/app/link.go` — основной бот отвечает на личные сообщения инструкцией; его обработчик не подходит для поддержки без изоляции.
- `internal/integration/max/{client,messages,updates,subscriptions}.go` — тонкий клиент и DTO. Текущий `SendUserMessage` всегда использует markdown и не подавляет тела в `outbound_request`.
- `internal/platform/outbound/client.go` — уже есть `Sensitive`, `NoRetry`, `RecordBody`; повтор создания сообщения после сетевого сбоя требует отдельной политики.
- `internal/platform/realtime/`, миграция `00107` — транзакционные SSE-инвалидации без содержимого; новый WebSocket не нужен.
- `internal/platform/httpx/auth.go`, `internal/bootstrap/server.go` — `AdminAny` (`moderator`, `senior`), сессия, CSRF, AdminGate и OpenAPI.
- Фронтенд: `src/pages/adm-dispute/ui/AdmDisputePage.tsx`, `src/entities/admin-placement/api/adminDisputeApi.ts` — образцы переписки и запросов; поддержку хранить отдельной сущностью.
- `src/features/contact-support/ui/SupportMenu.tsx` сейчас только открывает внешние контакты, `VITE_SUPPORT_MAX_URL` уже существует.

Официальные источники, проверены 2026-11-18:

- [Webhook](https://dev.max.ru/docs-api/methods/POST/subscriptions/): HTTPS, заголовок `X-Max-Bot-Api-Secret`, при активной подписке Long Polling не работает.
- [Отправка сообщений](https://dev.max.ru/docs-api/methods/POST/messages): текст/вложения, до 4000 символов текста, ограничение 2 сообщения/с на диалог. Успех API означает принятие MAX, а не прочтение человеком.
- [Загрузка вложений](https://dev.max.ru/docs-api/methods/POST/uploads): загрузка файла и токен вложения, возможен временный отказ `attachment.not.ready`.
- [Медиасообщения](https://dev.max.ru/docs-api/use-cases/sending-messages/media/): поддержаны `image/video/audio/file`; видео и аудио отправляются через предварительную загрузку и token, не по произвольному URL. `audio` подтверждён документацией; отображение записи как нативного голосового пузыря MAX требует отдельной проверки, его нельзя обещать по наличию типа audio.
- [Информация о видео](https://dev.max.ru/docs-api/methods/GET/videos/-videoToken-/): при необходимости получать доступные видеоисточники по video token через worker; не предполагать, что любой входящий видеопayload содержит готовый файл.

## Результат и границы первой версии

Администратор открывает «Поддержку», видит новые обращения, выбирает человека, читает историю и отвечает от имени бота. Пользователь продолжает обычную переписку с ботом MAX и не обязан иметь аккаунт Chanly.

Включить:

- Список диалогов: имя/username MAX при наличии, последнее сообщение, время, число непрочитанных, статус, ответственный; поиск по имени, username и MAX ID, фильтры «Нужен ответ», «Открытые», «Закрытые», «Мои».
- Историю входящих и исходящих сообщений, автора-оператора, дату, пометки редактирования/удаления и состояния отправки; подгрузку старых сообщений.
- Текст и двустороннюю передачу картинок, видео, аудио/голосовых и файлов. В админке — просмотр скриншотов, видеоплеер, аудиоплеер с длительностью/перемоткой и скачивание с проверкой прав; у оператора — запись голоса с микрофона, предварительное прослушивание, отмена и отправка. Для иных типов показать понятную карточку типа; не терять само обращение из-за неподдерживаемого вложения.
- Ответственного, закрытие/повторное открытие, общую историю для нескольких администраторов; защиту от конфликтующих изменений.
- Счётчик обращений, требующих ответа, в меню и обновление без перезагрузки. Настольные/почтовые/Telegram-уведомления, шаблоны ответов, внутренние заметки, SLA, AI-ответы и CRM — отдельные расширения.

Допущения планирования, можно изменить до соответствующей задачи:

- Один постоянный диалог на `(support_bot_id, max_user_id)`; новое сообщение после закрытия открывает тот же диалог. `bot_started` сам по себе не создаёт пустое обращение.
- Доступ имеют обе действующие роли администратора; новая роль оператора пока не вводится.
- «Непрочитано» — персонально по оператору; «Нужен ответ» — общее состояние очереди, очищаемое только подтверждённым ответом MAX на просмотренную часть истории. Новый входящий во время отправки сохраняет признак ожидания.
- Общение не привязывается к организации по совпадению имени/username. В первой версии достаточно внешнего MAX ID; ссылки на аккаунт допустимы только по уже доказанной связи.
- История гарантируется с момента включения приёма. Автоматический импорт прошлой переписки не обещать без отдельной проверки возможностей MAX.
- Рабочие лимиты вложений первой версии, настраиваемые по типу: картинка/обычный файл — 20 МБ, видео — 250 МБ, аудио/голосовое — 50 МБ, запись оператора — до 10 минут; до 5 вложений в сообщении с учётом допустимых MAX сочетаний типов. Это лимиты продукта, а не заявления о максимумах MAX. Согласовать с body/timeouts edge и storage. Входящий файл сверх лимита получает видимую пометку, текст обращения сохраняется.
- Срок хранения закрытой переписки и файлов — настраиваемый; предлагаемый исходный срок 180 дней после закрытия, служебных payload входящих — 7 дней после успешной обработки. Зафиксировать выбранные значения в эксплуатационной конфигурации перед включением очистки; незавершённые отправки не удалять.

## Предлагаемый HTTP-контракт

Все административные маршруты — под `/api/v1/admin/support`, в существующей защищённой цепочке:

| Метод и путь относительно `/api/v1` | Назначение |
|---|---|
| `GET /admin/support/conversations` | Фильтры, поиск, пагинация, `total`, unread и needs_reply |
| `GET /admin/support/conversations/{id}` | Карточка, статус, ответственный, версия |
| `GET /admin/support/conversations/{id}/messages` | История со стабильным курсором `(sequence,id)` |
| `POST /admin/support/conversations/{id}/messages` | Текст/ID вложений + клиентский ключ идемпотентности; `202` и сохранённое сообщение |
| `POST /admin/support/conversations/{id}/read` | Монотонная отметка до конкретного sequence, не до текущего времени |
| `PATCH /admin/support/conversations/{id}` | Статус/ответственный с ожидаемой версией, конфликт — `409` |
| `POST /admin/support/messages/{id}/retry` | Явный повтор известного отказа; защита от одновременных повторов |
| `POST /admin/support/attachments` | Ограниченная multipart-загрузка в приватное хранилище поддержки |
| `GET /admin/support/attachments/{id}` | Авторизованное чтение, поддержка HTTP Range для перемотки видео/аудио, без раскрытия URL/токенов MAX |
| `POST /webhooks/max-support/{secret}` | Отдельный webhook, без сессионной авторизации, с собственными path/header-секретами |

Точные DTO и имена operationId закрепить в T1. ID MAX передавать строками в JSON, чтобы JS не терял точность int64. Диалог/сообщение/вложение внутри приложения — UUID v7.

## Критерии приёмки

1. Текст, картинка, видео и голосовое пользователя в support-боте появляются в «Поддержке» с историей и нужным счётчиком; картинка открывается, видео/аудио воспроизводятся и перематываются, повтор webhook не дублирует сообщение.
2. Ответ админа попадает тому же пользователю от support-бота; queued, sent, failed и unknown различимы и правдиво названы.
3. После потери ответа MAX workflow не отправляет сообщение повторно автоматически; HTTP retry сохраняет клиентскую идемпотентность.
4. Два оператора могут работать одновременно без потери read markers, конфликтующих назначений и нового входящего, который был ошибочно помечен отвеченным.
5. История, файлы и SSE доступны только администраторам; технические журналы и job payload не содержат переписку или секреты.
6. Основной бот каналов, уведомления, споры и остальные разделы админки продолжают работать.
7. Backend/mock/frontend согласованы по OpenAPI, целевые проверки выполнены; оба независимых выпуска описаны и документация обновлена.
8. Админ отправляет картинки/видео/аудио и записывает голос с микрофона с прослушиванием и отменой; пользователь получает медиа через MAX. Передача audio и его отображение как нативного голосового проверяются и описываются раздельно.
