# Промпт для планирования фронтенд-правок

Готов к передаче в отдельный чат проекта `D:/work/maxim-frontend`. Это запрос на составление плана, не на реализацию. Состояние контрактов основного backend-плана актуализировано по коду dev от 2026-11-14: optional signer_basis, senior GET категорий и атомарный PATCH с prices реализованы локально. Полный штатный Go race-набор на настоящих Testcontainers/PostgreSQL, включая Mailpit, MinIO и Caddy/SSE, завершился с кодом 0 без overlay и фильтров тестов; сборка Docker-образа также прошла. Дополнительно после разрешения пользователя успешно выполнен opt-in тест публичной песочницы Т-Банка с синтетическими данными, HTTP 200; непроверенных тестов из-за исключений не осталось. Детали в backend-плане. Деплой не выполнялся; готовность стенда проверять отдельно.

---

Используй `$aif-plan` и составь подробный план только фронтенд-правок в `D:/work/maxim-frontend`. Сначала прочитай AGENTS.md, `.ai-factory/config.yaml`, описание/архитектуру и project skill-context; соблюдай FSD и существующий UI kit. Ничего не реализуй, не деплой и не коммить. Не переключай ветки ради планирования. Настройки уже согласованы: тесты критичных сценариев, стандартные логи без персональных данных, актуализация затронутой API/UI-документации. Пользователь хочет русский план с файлами, зависимостями и критериями приёмки. Не спрашивай повторно о режиме планирования.

Backend находится в `D:/work/maxim`, его единственный HTTP-контракт — `api/openapi.yaml`, а generated frontend types обновляются штатным `yarn api:types`. Прочитай:

- `.ai-factory/plans/product-feedback-backend.md`;
- `.ai-factory/plans/platform-fee-25-backend.md`;
- `.ai-factory/plans/first-image-ad-label-backend.md`.

Эти планы НЕ доказывают, что изменения уже реализованы или выложены. Сверь API-код/спецификацию и при возможности версию доступного стенда. Отдели задачи, доступные сейчас, от зависимых от нового backend. Не добавляй клиентскую имитацию ещё не существующего server contract.

Исходные правки (сохранить номера, 7 отсутствует):

1. **Самозанятый регистрируется без документа налогообложения.** Backend это уже разрешает. Убрать обязательность/блокировку формы, согласовать тип/схему/подсказки; необязательная загрузка не должна мешать регистрации. Проверить `features/register-organization/` и API организации.
2. **Кнопка поддержки с выпадающим меню из двух ссылок — Telegram и MAX.** Найти существующий пункт поддержки/общий layout. Использовать реальные адреса из конфигурации/материалов проекта; если их нет, запросить ровно эти ссылки и продолжать независимое планирование. Не подставлять вымышленные аккаунты. Предусмотреть клавиатуру, focus, Escape/клик вне, мобильную раскладку. Backend endpoint для двух ссылок не нужен.
3. **Основание полномочий подписанта юрлица необязательно.** Backend принимает отсутствие обоих signer_basis_name/signer_basis_number или только одного, в регистрации/добавлении кабинета/PATCH. Пропуск PATCH сохраняет значение, пустая строка очищает. Убрать required только с этих двух полей; должность/ФИО подписанта и КПП остаются обязательными.
4. **Категории управляются из админки, поиск — по загруженному справочнику.** Реализован GET /admin/channel-categories для senior: items с id/slug/name/position/archived, включая архив, сортировка position, slug. Использовать существующие POST/PATCH; восстановление archived=false, UUID/slug не меняются. GET /channel-categories возвращает полный активный набор; поиск клиентский, q не нужен. При редактировании канала с прежней архивной категорией показывать сохранённый ID/«Архивная категория» и опускать category_id до активного нового выбора; передача архивного ID даёт 422 category_id. Фиксированный список добавлений не нужен.
5. **После успешного сохранения данных канала открывать «Мои каналы».** Найти фактический route списка; переходить только после успешного ответа общего сохранения. При ошибке оставить введённые данные и показать ошибки полей. HTTP redirect с бэка не нужен.
6. **Одна кнопка сохранения канала.** Реализован PATCH /blogger/channels/{id} с optional prices: элементы {format_id, amount, is_enabled}, полный набор вместо двух последовательных запросов. Профиль и цены фиксируются атомарно; 200 BloggerChannel содержит результат. Omitted prices сохраняет цены, массив заменяет, null запрещён, пустой массив допустим только вне исходного и итогового active. На ошибке сохранить введённую форму и показать детали, на 200 открыть «Мои каналы». Старый PUT /prices остаётся совместимым.
8. **Понятная проверка статуса в выплатах.** Исследовать `features/rocketwork-connect/ui/RocketworkCard.tsx` и сущности выплат. `GET /blogger/rocketwork` даёт `required/status/next_action/status_checked_at`; POST `/refresh` асинхронно ставит job и возвращает текущий, возможно прежний статус. Для active показывать «Подключено» без основной кнопки refresh; required=false не требует подключения. Для none/invited/pending/blocked показать осмысленное действие по next_action и объяснение. После refresh сообщать «Проверка запрошена», ждать повторным GET/SSE с ограниченным polling и таймаутом; завершать ожидание и при прежнем status, если изменился status_checked_at. Остановить polling при уходе со страницы. Не путать статус подключения с выплатой/диагностикой controlled-dev. Учитывать 10 refresh/час, 429/503, loading и отсутствие результата за отведённое время. Фоновую серверную проверку не отключать.
9. **По умолчанию меню развёрнуто.** Найти layout/sidebar и persisted preference. Согласовать desktop default expanded и мобильный drawer с текущими breakpoints; сохранить явное действие пользователя, не разворачивать заново на каждом route. Не создавать горизонтальную прокрутку на мобильном.
10. **Поменять цвет кнопки со статусом в корзине.** Найти фактический статус, его контекст и существующие semantic tokens; предложить конкретный цвет/состояния в плане, если точный цвет не задан. Учитывать hover/focus/disabled/loading и контраст. Не изменять серверные состояния корзины ради оформления.
11. **Комиссия площадки 25%, не 15%.** Показ цен определяется backend, комиссия начисляется СВЕРХ цены блогера. Не рассчитывать отдельно жёстко заданные 25% поверх уже готового total_amount; не путать с удержанием из выплаты/комиссией провайдера. Найти тексты «15%», tooltip и локальные демонстрационные данные. Синхронизировать UI с отдельным backend-планом: исторические заказы могут иметь snapshot 15%, новые — 25%; изменение цены корзины должно показываться и подтверждаться штатным способом. Результаты API остаются источником истины.
12. **Каналы обрезаются при создании кампании.** Воспроизвести отдельно потерю страниц и визуальное обрезание карточек. Каталог: `GET /catalog/channels`, default limit=20, max=100, `next_cursor`; читать все нужные страницы через существующий RTK Query pattern, сохранять выбранные каналы между страницами, сбрасывать cursor при смене фильтров, исключить дубли. Проверить >20/>100 каналов, длинные названия, overflow/высоту/скролл и загрузку следующих страниц. Не отключать пагинацию на сервере. Если HTTP-обход корректен, исправление целиком фронтенд.
13. **Аккуратная маркировка и только первая картинка.** Backend отдельным планом меняет стиль/версию производной и выбор картинки. Использовать media_urls/preview с сервера, не накладывать вторую CSS-плашку на файлы и не маркировать все изображения клиентом. Сопоставить порядок preview и опубликованной версии, проверить перестановку/удаление первой и loading. Старые immutable post versions могут сохранять старый стиль. Точный дизайн серверной плашки согласуется отдельно, клиент не должен маскировать серверное расхождение.
14. **Предпросмотр как в MAX — фон и декоративные стикеры.** Исследовать `widgets/post-editor/ui/PostPreviewCard.tsx` и его CSS. Добавить подложку чата как слой UI, отдельно от реального содержимого/изображений поста. Подложка не попадает в media upload, публикацию, ОРД или текст. Сохранить адаптивность, читаемость, границы длинных сообщений и корректную разметку медиа.
15. **Абзацы редактора выглядят иначе, чем MAX.** Исследовать `widgets/post-editor/ui/PostTextEditor.tsx`, preview и backend serializer. Backend paragraph уже сериализуется в перенос `\n` без HTML `<p>`; не удалять paragraph из API и не склеивать смысловые переносы. Согласовать margin/line-height, Enter/Shift+Enter, пустую строку, вставку текста и preview. Сравнить editor → preview → payload/пост на одинаковом примере; отдельное backend-изменение только при доказанном расхождении.
16. **Календарь не даёт выбирать прошлые даты.** Найти все затронутые календари, прежде всего период кампании/публикацию. Disable прошлые значения и валидировать ручной ввод, диапазон и текущую дату при сохранении; backend кампаний использует MSK (Europe/Moscow), а не timezone браузера/автора запроса. Проверить MSK-полночь, date-only vs timestamp, lead time и смену даты при открытой форме. Календарь недоступности канала имеет иной сценарий (начавшийся интервал с будущим концом допустим backend); его изменение выделить и согласовать отдельно, без молчаливого глобального запрета.
17. **Убрать отдельную кнопку «Сохранить требования», валидировать по вводу.** Поле — `extra_requirements` кампании, уже есть PATCH `/campaigns/{id}`, максимум 2000 Unicode-символов, пустая строка допустима, менять можно только draft. Исследовать `features/edit-campaign-requirements/ui/RequirementsForm.tsx`. Выбрать одну понятную модель: сохранение с общей формой либо аккуратный autosave с debounce; не отправлять PATCH на каждый символ и не считать JS UTF-16 length эквивалентом Unicode-символов сервера. При autosave нужны индикатор ошибки/сохранения, сериализация запросов/защита от поздних ответов, только изменяемое поле, flush перед следующим шагом/checkout, защита от ухода с несохранённым текстом. Новый backend validation endpoint не нужен.

Составь план с конкретными проверенными файлами, зависимостями от backend, критериями UX и тестами ключевых сценариев. Сгруппируй по регистрация/каналы/кампании/выплаты/общий layout, избегай повторных задач на одни компоненты. Проверь состояния loading/error/empty, клавиатуру и основные размеры 360/390/768/1440. Для будущей реализации указать штатные `yarn api:types`, `yarn verify`, целевые Vitest/Playwright и визуальную проверку критичных экранов. Не добавляй бессодержательные snapshot-тесты и не запускай реализацию из этого запроса.

Отдельно обозначь только оставшиеся продуктовые вопросы: реальные ссылки поддержки, желаемый цвет статуса, образец внешнего вида предпросмотра/плашки при необходимости. Категории уже решено редактировать из админки, спрашивать фиксированный список не нужно. Не блокируй остальное планирование на этих деталях.
