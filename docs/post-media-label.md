# Рекламная плашка на первой картинке

Новые версии поста с `token_carrier=media` используют плашку v2 только на позиции 0 сохранённого `media_file_ids`. Для `[A,B,C]` выбираются `[labeled(A,v2),plain(B),plain(C)]`. При `token_carrier=text` весь альбом plain, маркировка остаётся в тексте. erid по-прежнему находится в тексте или ссылках по `token_position`, на картинку не переносится.

## Изображения и предпросмотр

Plain — копия исходного изображения без серверной плашки, после EXIF-поворота и удаления метаданных. Исходники медиатеки не меняются. JPEG/PNG/WebP обрабатываются прежним способом и с прежними лимитами. Дизайн v2 — реализованный рабочий вариант предложенной в плане карточки: тёмный непрозрачный фон, белая кириллица Go Bold, поля, скругление, многострочное название; полные параметры — в [§6.2](06-finance-legal.md#62-плашка).

При reorder `[A,B,C] → [B,A,C]` будущая версия выбирает labeled B и plain A/C. Оба способа удаления первого файла — сохранением черновика и удалением из медиатеки — готовят новую первую производную. Удаление из медиатеки обновляет все затронутые черновики организации и jobs в одной транзакции. SaveDraft, CreateVersion, Delete и enqueue preview используют общую транзакционную advisory-блокировку организации до блокировок строк поста/медиа.

`POST /campaigns/{id}/post/preview` возвращает полный альбом в сохранённом порядке или `media_urls: []` с `media_processing`, пока хотя бы одна выбранная производная не готова. Это изменяет прежнюю частичную выдачу ссылок. Готовая plain не заменяет pending labeled. Создание версии при неполной готовности возвращает `409 post_not_ready`, без частичного snapshot. Нулевой альбом при явно выбранном media сохраняет `media_required_for_token`.

## Snapshot, MAX и ОРД

Snapshot фиксирует точные DerivativeID и позиции. MAX загружает private-объекты этих производных; ОРД получает их public-копии в том же порядке и ждёт все ссылки. Разные URL не означают разные картинки: совпадение проверяется по содержимому файлов. Условный erid/UTM в тексте preview не являются итоговым текстом версии.

Все существующие версии, в том числе pending/approved, сохраняют исходные файлы. Исторический v1-альбом с плашкой на каждом кадре остаётся допустимым. Черновик, реквизиты, новый шаблон, soft-delete и purge не меняют его DerivativeID, public URL, erid и креатив. Для нового содержания требуется новая версия и новая регистрация.

## Согласованное обновление

Новых флагов конфигурации и миграций схемы нет. `PlateTemplateVersion=2` меняет hash только labeled. Plain/preview сохраняют RenderVersion=1; cache/dedupe по файлу/виду/hash и публикация по DerivativeID работают как прежде. Исторические файлы не перестраиваются.

1. На время обновления ограничить новые изменения медиа и создание версий. Дать старым builders завершиться, затем остановить их.
2. Обновить API и все media workers согласованным выпуском. Не допускать потребления новых v2 jobs старыми workers: старый код вычисляет v1 hash и пропускает их как stale_params.
3. Возобновить операции. SaveDraft/Preview лениво подготавливают текущие v2/plain для активных черновиков; Delete подготавливает затронутые черновики сразу. После старого stale skip повторный SaveDraft/Preview может поставить актуальную работу заново.
4. На изолированных fake проверить reorder/remove-first, готовность всех файлов и сохранность старой версии. Следить за media_processing, stale_params и ошибками построения/публикации; не регистрировать старые креативы повторно. Этот порядок не является разрешением на фактический deploy или live-вызовы MAX/ОРД.

## Откат и диагностика

Предпочтителен исправляющий совместимый релиз с поддержкой v2. Перед полным откатом ограничить новые операции и остановить builders. Pending v2 не отдавать старому worker; после возврата совместимого кода восстанавливать актуальную работу через SaveDraft/Preview. Старый выпуск вновь создаёт версии по старой политике, то есть first-only до исправления отменяется. Существующие snapshot и public samples продолжают читаться по ID и не заменяются v1, не удаляются и не перерегистрируются.

Если preview пуст, проверить `problems`: media_processing означает ожидание точных выбранных вариантов; requisites_missing — нехватку реквизитов; media_required_for_token — пустой альбом с media. Не подменять файл, чтобы обойти ожидание. INFO сообщает результаты сохранения/удаления/создания версии, WARN — причины блокировки, DEBUG — position/kind/render_version и безопасные ID; уровень регулируется существующей настройкой. Названия, ИНН, текст, erid, подписанные URL и upload-токены в добавленные логи не выводятся.

## Проверка

Тесты используют fake MAX/ОРД/storage и настоящую изолированную PostgreSQL в testcontainers. Для обязательного прогона использовать `CI=true`, чтобы отсутствие Docker не маскировалось пропуском. Целевые пакеты: `internal/post/...`, `internal/marking/app`, `internal/placement/app`; штатные проверки: sqlc generate/vet, go generate ./internal/apigen, go vet ./..., go test -race -count=1 ./.... Внешние аккаунты и рабочие секреты не нужны.
