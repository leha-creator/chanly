# Настройки аккаунта: контракт для фронтенда

Все пути ниже относительно `/api/v1`. Нужна cookie `session`; все изменения требуют
`X-CSRF-Token`, равный cookie `csrf_token`. Формат ошибок прежний: `error.code`,
`error.details`, `request_id`. Настройки принадлежат **пользователю**, одинаковы во
всех его сеансах и устройствах и сохраняются после выхода.

## Операции

| Запрос | Результат |
|---|---|
| `GET /me/settings` | Версия, приватность, тихие часы, сохранённые переключатели и эффективный каталог |
| `PATCH /me/settings` | Частичное обновление; обязательна прочитанная `version`; ответ — полное подтверждённое состояние |
| `GET /notifications/{id}` | Собственное уведомление по ID из live-события; чужое/удалённое — 404 |
| `POST /me/email-change` | `{new_email}`; 202 с `id`, `expires_at`, `resend_at` |
| `POST /me/email-change/{id}/resend` | Заменить оба кода; 202 с прежним сроком действия |
| `POST /me/email-change/{id}/confirm` | `{current_code,new_code}`; 204 только после атомарной смены |
| `GET /me/sessions` | Активные собственные сеансы с безопасным ID и `current` |
| `DELETE /me/sessions/{id}` | Завершить другой собственный сеанс; 204 |
| `DELETE /me/sessions/others` | Завершить все остальные, сохранив текущий; 204, повтор безопасен |
| `POST /auth/logout` | Штатный выход из текущего сеанса с удалением cookie |

`GET /me` остаётся источником почты, последнего входа, кабинетов и организаций.
Администратор может не иметь организации. `organization.name` — название
организации, а не личное имя. Реквизиты — существующий
`GET /organizations/current`. Новая копия этих данных в настройках не создаётся.

## Сохранение и ошибки

Пример частичной записи:

```json
{
  "version": 4,
  "hide_notification_preview": true,
  "delivery": [
    {"group":"advertiser.placements","event":"*","channel":"email","enabled":false},
    {"group":"advertiser.placements","event":"placement.accepted","channel":"browser","enabled":true}
  ]
}
```

Только переданные поля и переключатели меняются. `delivery` — патч по ключу
`group,event,channel`, не замена всего списка. Дубликат ключа — 422 `duplicate`.
`event="*"` меняет значение по умолчанию для группы; индивидуальный переключатель
события имеет приоритет, обязательная почтовая доставка имеет высший приоритет.
Чтобы выключить всю группу с ранее включёнными событиями, отправьте также их
индивидуальные переключатели; отключение группы не стирает исключения.

Сохранение блокирует строку и проверяет версию в одной транзакции. Два запроса с
одной версией не могут оба успешно сохраниться. 409 `conflict`,
`details.reason=version_conflict`, `current_version` — перечитать GET и повторить
только всё ещё желаемые изменения на новой версии. Не отправлять старый полный
снимок поверх чужих изменений. Успешный ответ увеличивает версию на один.

| Состояние | Обработка во фронтенде |
|---|---|
| Pending | Сохранение ещё не подтверждено; сериализовать быстрые правки либо разрешать конфликт версий |
| 401 `unauthorized` | Штатный выход, остановка runtime, очистка данных прежнего пользователя |
| 403 `forbidden`, `csrf` | Ошибка CSRF; не показывать «Сохранено» |
| 403 `delivery_unavailable` | Кабинет/канал более недоступен; перечитать каталог |
| 422 `validation_failed` | Показать ошибку поля; `mandatory`, `invalid_interval`, `duplicate` — причины в `details.reason` |
| 409 `version_conflict` | Перечитать и согласовать правки |
| Ошибка сети/5xx | Состояние неизвестно; перечитать GET перед повтором |

## Каталог и доставка

`catalog` — плоский список переключателей: `group`, `event`, `channel`, эффективные
`enabled`, `available`, `mandatory`, необязательный `reason`. Строки с `event="*"`
представляют групповые переключатели. Недоступные каналы имеют `available=false`
и `enabled=false`; сервер отвергает попытки записать их. Для недоступного кабинета
вообще нет групп. Не строить доступность по предположениям о роли пользователя.

Список формируется из действительного `notification/domain.Catalog()`:

| Группа | События |
|---|---|
| `advertiser.placements` | `placement.accepted`, `scheduled`, `rescheduled`, `declined`, `expired`, `cancelled`, `published`, `failed`, `removed` (все с префиксом `placement.`) |
| `advertiser.moderation` | `order.post_approved`, `order.post_rejected`, `order.erir_rejected` |
| `advertiser.finance` | `balance.deposited`, `closing_acts.ready` |
| `advertiser.disputes` | `placement.disputed`, `placement.dispute_resolved`, `placement.dispute_message` |
| `blogger.requests` | `placement.request`, `placement.accept_reminder` |
| `blogger.placements` | `placement.expired`, `cancelled`, `returned`, `published`, `failed`, `removed`, `removal_overdue` |
| `blogger.channels` | `channel.approved`, `rejected`, `suspended`, `disconnected`, `restored`, `blocked` |
| `blogger.payouts` | `payout.sent`, `payout.succeeded`, `payout.failed`, `rocketwork.active`, `rocketwork.blocked` |
| `blogger.disputes` | `placement.disputed`, `placement.dispute_resolved`, `placement.dispute_message` |
| `admin.publication_errors` | `placement.failed` |
| `admin.disputes` | `placement.disputed`, `placement.dispute_message` |

Префиксы в сокращённых ячейках наследуются от первого события. Новые события
модерации, финансов, согласований и ошибок ОРД для администраторов не выдумываются:
в текущем пользовательском каталоге их нет. Письма и чат дежурных из `platform/alert`
— отдельный эксплуатационный канал, не управляются личными настройками. Обе
существующие административные группы доступны `moderator` и `senior`; старшие
права на административные realtime-темы финансов по-прежнему проверяет SSE.

Каналы:

- `email`: по умолчанию включён для рекламодателя и блогера. Администратору
  недоступен с `reason=admin_alerts_separate`.
- `max_bot`: по умолчанию включён только для блогера, когда у владельца организации
  есть канал с известным `added_by_max_user_id`. Иначе `max_bot_unavailable`.
  Сохраняется существующая маршрутизация: одно сообщение владельцу через MAX ID
  **конкретного канала события**. Если у события нет такого канала/адресата, MAX
  не создаётся. Это не подтверждение доставки: запрет личного сообщения со стороны
  MAX по-прежнему может завершить доставку отказом. Произвольного MAX ID в API нет.
- `browser`, `sound`: по умолчанию выключены. Фронтенд применяет их к live-событиям.
  Настройка браузера не означает permission браузера; разрешение и проверку звука
  запрашивает только фронтенд. Web Push при закрытом сайте отсутствует.

**Обязательные события по email:** `placement.disputed`,
`placement.dispute_message`, `placement.dispute_resolved`, `placement.failed`,
`payout.failed`, `channel.blocked`, `channel.disconnected` — только для ролей,
которым событие предназначено и доступна почта. Для них `mandatory=true`,
`reason=required_obligation`. Отдельное выключение отвергается; групповой запрет
не меняет их эффективную включённость. Браузер, звук и MAX остаются добровольными.
Коды входа и подтверждения смены почты используют отдельные задания и никогда
не отключаются этими настройками.

Почта и MAX проверяют последние подтверждённые настройки **при каждой попытке
отправки**. Отключённая доставка становится `suppressed`, `last_error=settings_disabled`,
без внешнего вызова и расхода попытки; это не сбой интеграции. Повторное включение
не рассылает уже подавленные сообщения. Нельзя отозвать уже начавшийся внешний
вызов отправки. Кабинетная история всегда полная, с прежними правилами чтения и
сроком хранения, независимо от способов доставки.

## Тихие часы и приватность

`quiet_hours` целиком: `enabled`, `start`, `end` в `HH:MM`,
`timezone="Europe/Moscow"`. По умолчанию выключены, интервал `22:00–08:00`.
Начало включается, конец не включается; переход через полночь поддержан,
равные границы отвергаются. Время фиксировано по Москве (UTC+3).

Для необязательных email и всех MAX отправка откладывается до конца интервала
через существующий `job.Postpone` без расходования попыток. Сообщения не
объединяются и не теряются: после интервала отправляются обычной очередью;
настройки и часы снова проверяются. Если до отправки канал выключен, сообщение
подавляется. Обязательные email, коды входа/смены почты и эксплуатационные
оповещения дежурным обходят тихие часы.

Для `browser` и `sound` фронтенд проверяет тот же интервал и **пропускает** сигнал
во время тишины, не накапливает отложенные звуки и всплывающие окна.

`hide_notification_preview=false` по умолчанию. При true фронтенд маскирует
содержание панели колокольчика и browser notification, включая accessibility
атрибуты. Полная история и `GET /notifications/{id}` остаются доступны;
это настройка отображения, не ограничение доступа. Почта и MAX не маскируются.

## Новое уведомление, reconnect и resync

Существующие `/events` и `/admin/events` совместимы. Новые темы `invalidate`:

```json
{"version":1,"topic":"notification.created","object_id":"01900000-0000-7000-8000-000000000001","mode":"live"}
```

`object_id` — уникальный ID строки **кабинетного** уведомления, совпадает с `id`
из GET. INSERT создаёт сигнал, UPDATE/read/read-all/delete — только прежний
`notification.changed`. Транзакция откатывается — сигнала нет. Дедупликация
создания в БД не создаёт нового ID/сигнала.

При подписке сервер получает границу времени из PostgreSQL (тот же источник,
что `realtime_event.created_at`); отбрасывает сигналы создания до этой границы,
даже если reader увидел их после подключения. Часы API и БД сравнивать не нужно.
Долгая транзакция, создавшая запись до границы, не превращает её в новое оповещение
при позднем commit. Другие инвалидации по-прежнему доставляются для resync.

Replay отсутствует, `Last-Event-ID` не используется. Каждый `ready` после
первого подключения или reconnect и каждый `resync_required` требует перечитать
настройки и уведомления **без звуков и browser notification**. Потерянные во время
разрыва live-сигналы не догоняются; сама история восстанавливается GET. SSE даёт
онлайн-сигнал, а не обещание звука на каждое событие при отсутствии связи.

Алгоритм runtime:

1. Начать в muted-состоянии. На `ready`/resync заново прочитать `/me/settings` и
   `/notifications`; данные синхронизации никогда не оповещают.
2. После загрузки подтверждённых настроек принимать **только**
   `notification.created` с `mode=live`. На другие инвалидации обновлять кэш.
3. Дедуплицировать по `(user_id,notification_id)`. Получить уведомление через
   `GET /notifications/{id}`; 404/ошибка — пропустить сигнал. Прочитанное — пропустить.
4. По `notification.group`, `template` и `catalog` проверить канал и тихие часы,
   затем permission/autoplay. При скрытом предпросмотре использовать нейтральный текст.
5. Согласовать одну вкладку, выдающую сигналы (BroadcastChannel/эквивалент).
   SSE рассылается всем открытым клиентам; сервер не выбирает звучащую вкладку.
6. На `settings.changed` приостановить сигналы, перечитать настройки. На возврате
   вкладки также перечитать их. Пока GET не завершился успешно, сигналы выключены,
   предпросмотр нейтральный. Старые async-ответы после смены пользователя отбросить.

`settings.changed` не содержит значения настроек; всегда принадлежит одному
пользователю, включая admin stream. `notification.created` и `notification.changed`
также изолированы по пользователю, а не организации.

## Смена почты

Сервер нормализует адрес как существующий вход: trim + lower-case, уникальность
защищена `citext` и уникальным индексом. HTTP принимает email-формат до 254 символов.
Отдельные письма объясняют назначение кодов: владение текущим аккаунтом и новым
адресом. Никакой смены адреса до успешной проверки **обоих** кодов нет.

- Challenge действует 10 минут; одноразовый, привязан к пользователю, ID операции,
  назначению каждого кода и новому адресу. Коды входа не подходят.
- Не более 3 новых challenge на пользователя в час; новый гасит предыдущие.
- Всего 5 неверных пар кодов на challenge; расход попытки фиксируется даже при 422.
- Не более 3 отправок пары (первая + 2 повтора), интервал минимум 60 секунд.
  Повтор заменяет оба кода, не сбрасывает попытки и не продлевает 10 минут.
- В заданиях код и адрес зашифрованы существующим Sealer; payload затирается
  worker после завершения. Старые задания после resend/погашения не отправляются.
- Подтверждение блокирует адреса тем же механизмом, что вход/выдача login-кода,
  затем пользователя и challenge. Гонки с регистрацией защищены уникальным индексом.
- При успехе атомарно меняется email, гасятся активные login-коды обоих адресов и
  отзываются остальные сеансы. Текущий сохраняет cookie и права. SSE прежних
  сеансов закрывается штатной проверкой доступа; текущий получает `session.changed`.
- Просроченные записи очищаются общей cleanup с `Retention.AuthCode` после срока
  действия. Хеши, коды, адреса и payload в логи этой операции не записываются.

Ошибки: 409 `conflict`, `reason=email_taken`; 422 `validation_failed` с
`field=code`, `reason=invalid_code|expired_code|consumed_code`; 429 `rate_limited`
со scope `email_change`, `email_change_attempts`, `email_change_sends` или
`email_change_resend`, заголовок `Retry-After`. Чужой/несуществующий challenge — 404.
После 204 перечитать `/me` и `/me/sessions`; после 429 сохранить введённый адрес и
показать задержку. Коды и challenge не сохранять между сеансами.

## Сеансы и документы

Список возвращает только активные собственные сеансы: ID, текущий, исходный
`user_agent` при наличии, создание, последнее известное использование и срок.
Токены, хеши, IP и cookie отсутствуют. `last_active_at` — существующая отметка
продления сеанса (обновляется не чаще раза в час), не точный online-статус.
`user_agent` — недоверенная строка для безопасного текстового отображения.

Чужой/истёкший/уже отозванный выбранный сеанс — 404. Попытка удалить текущий
через DELETE — 422 `use_logout`; для него использовать `/auth/logout`.
Отзыв немедленно запрещает новые запросы; уже идущие запросы не отменяются.
SSE проверяет доступ перед каждым кадром и каждую секунду, с таймаутом проверки
2 секунды; при отзыве/ошибке проверки закрывается. После reconnect запрос получит 401.

Документы — существующий `GET /legal-documents`: `published_at` относится к
публикации версии, `accepted` — к её принятию текущей организацией. Без организации
принятие отсутствует. Дата принятия в этом API не предоставляется: показывать
статус, не подставлять дату публикации. Не заменять сбой GET статусом «не принято».

## Миграция, генерация и проверка

`00108_account_settings.sql`: таблицы `user_settings`, `email_change`, индексы,
пользовательский триггер `settings.changed`, INSERT-only `notification.created`,
статус доставки `suppressed`. Down снимает триггеры/таблицы и переводит suppressed
в failed перед восстановлением прежнего ограничения статусов.

Контракт — [OpenAPI](../api/openapi.yaml); `go generate ./internal/apigen`,
`sqlc generate`; в `mockapi/`: `go generate ./internal/api ./internal/store`.
Политика и каталог mockapi генерируются из production domain, без сетевой доставки.
Mock-коды: текущая почта `000000`, новая `111111`; resend оставляет эти фиксированные
значения. CSRF, внешняя отправка и реальные данные устройства в mockapi не эмулируются.

Проверки: `go test ./...` из корня (Docker обязателен для PostgreSQL), отдельно
`go test ./...` в `mockapi/`. Основные новые сценарии:
`internal/bootstrap/account_settings_test.go`, доменные тесты настроек/почты,
`internal/platform/realtime/notification_test.go`, контрактный `TestEveryOperation` mockapi.

В этот объём не входят Web Push, экспорт/удаление аккаунта, отзыв юридических
согласий, аватары, пароли и новый каталог административных бизнес-событий.
