## Решение по агентской модели

Владелец выбрал **агент** в текущей сессии. Для закрытия Q-02 юрист и бухгалтер подтверждают, кого представляет платформа, кто заключает договор с блогером, комиссию/доход, удержания и возвраты, состав закрывающих документов. С ОРД сверить Q-14/Q-39/Q-43. Записать дату, ответственных и ссылку на согласованный документ.

Затронуты `internal/marking/`, `internal/ledger/`, `internal/billing/`, `internal/payout/`, `ORD_INITIAL_*`, `ORD_PUBLISHER_*`, `ORD_INVOICE_TYPE_*`, шаблоны документов. При расхождении сначала определить необходимую переработку; не менять денежную семантику одним переключением конфигурации.

## Изолированный стенд и сценарии

1. Отдельные БД и S3-корзины по [deploy/app](../../deploy/app/README.md). На staging `APP_ENV=development`; `APP_ENV=test` принудительно включает MAX/ОРД fake. Токены нужны для live.
2. ОРД — только `https://ord-prestable.yandex.net`, `ORD_REPORT_AUTO_SEND=false`; RW — disabled до подтверждения контракта. Production-данные не копировать.
3. Проверить api/worker командой `maxim config check`. Preflight интеграции не доказывает сеть, права или совместимость API.
4. MAX: чтение бота/канала/прав/списка сообщений; пост человека; тестовый пост с форматированием и альбомом; события, просмотры, удаление через 72 часа. Наблюдать Webhook в api/worker, не менять подписку рабочего бота.
5. ОРД: контрагент → договоры → площадка → креатив/erid → статистика → акт/разбивка; дождаться конечного статуса; повторить после частичного успеха. Не предполагать возможность удаления объектов.
6. RW: онбординг → депозит → тестовая выплата → статус/чек; повтор, неизвестный исход, неверная подпись, порядок событий и опрос. Реальные деньги не использовать.
7. Доказательства добавлять в матрицу по мере проверки. Fixtures обезличивать; локальные тесты не должны требовать внешних токенов. Длительное ожидание и отсутствие доступа оставляют этап открытым.

На сервере использовать уже настроенное окружение контейнера.

```sh
# Без сетевых вызовов и подключения к базе. Успех = только корректные настройки.
maxim integration-check --system max
maxim integration-check --system ord

# Только чтение: бот, канал, членство администратора, последние сообщения.
maxim integration-check --system max --scenario inspect --execute

# Создаёт один технический текстовый пост в выделенном канале.
maxim integration-check --system max --scenario publish --execute --run-dir /private/checks/max-001
maxim integration-check --system max --scenario observe --execute --run-dir /private/checks/max-001

# Только после реальных 72 часов; таймер не ускоряется флагами CLI.
maxim integration-check --system max --scenario remove --execute --run-dir /private/checks/max-001

# Если отправка завершилась неизвестным исходом: поиск, никогда повторный POST.
maxim integration-check --system max --scenario recover --execute --run-dir /private/checks/max-001
```

Можно передать `--chat ID`, но он обязан совпасть с `INTEGRATION_CHECK_MAX_CHAT_ID`. Код выхода 0 — шаг завершён, 1 — блокировка/ошибка/невыдержанный срок, 2 — неверные аргументы. `preflight` всегда выводит `live_verified=false`; наличие просмотров/постов в `inspect` не закрывает вопросы об их полноте и обновлении.

Каталог `--run-dir` содержит `state.json` с UUID запуска, ботом, каналом, ID поста, хешем и временем. До внешнего изменения сохраняется промежуточное состояние. Повтор `publish` после попытки запрещён; `recover` ищет маркер запуска и начинает новый консервативный отсчёт 72 часов. Если поиск не нашёл пост, исход остаётся неизвестным: сверить канал вручную, не создавать новый запуск вслепую. Поиск ограничен возможностями существующего адаптера, поэтому отсутствие в выдаче не доказывает отсутствие публикации.

В диагностическом клиенте отключены HTTP-перенаправления и внутренние повторы outbound. Настройки повторов рабочего приложения не меняются. После временного сбоя чтение можно повторить отдельным запуском; после неопределённого результата записи сначала сверить состояние. Общие логи содержат request_id, шаги сохранённого прогона — run_id. Тела ошибок провайдера и URL диагностическая команда не печатает.

`run.lock` исключает одновременные процессы одного запуска. После аварийного завершения удалить только этот lock вручную, установив, что процесс остановлен; `state.json` не удалять. Отсутствие поста до подтверждённого DELETE не считается успешной проверкой удаления. При потере ответа DELETE исход требует ручной сверки. Для удаления после семи суток просто выполнить `remove` позже; результат 72 часов не доказывает семисуточную границу.

Команда пока автоматизирует только текстовый цикл MAX. Альбом, вложенные стили и Webhook проверяются по сценарию выше на стенде; сырые ответы команда не экспортирует. ОРД поддерживает только preflight, RW всегда блокируется до подтверждения контракта. Не использовать эту команду как свидетельство завершения всего этапа.

## Журнал и доступы

DEBUG — шаги; INFO — результат; WARN — блокировка/неизвестный исход; ERROR — сбой. Включать run_id и correlation ID. Исключить токены, секретный URL Webhook, полные ответы, ИНН, чужие посты, чеки и реквизиты.

Настройки — вне git с ограниченными правами. При смене исполнителя/компрометации отозвать токен у провайдера, обновить api/worker и повторить проверку. Подписку MAX менять согласованно с владельцем тестового бота. TLS-проверку не отключать. Артефакты запусков хранить в отдельном локальном каталоге и не удалять до сверки неизвестного исхода.
