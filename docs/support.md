# Поддержка пользователей через MAX

Администраторы `moderator` и `senior` работают в `/adm/support`: выбирают обращение,
читают историю и отвечают от имени отдельного бота поддержки. Пользователю достаточно
написать боту; регистрация в Chanly не требуется. Основной бот каналов продолжает
работать независимо. История сохраняется с момента подключения webhook, старые сообщения
автоматически не импортируются.

## Работа оператора

Экран устроен как мессенджер и занимает доступную высоту окна: очередь слева,
компактная шапка диалога сверху, история и однострочное поле ответа снизу.
Поле растёт при вводе нескольких строк. На телефоне очередь и диалог открываются
по отдельности. Дата показана разделителем, время и состояние — внутри сообщения;
галочка «Принято MAX» означает приём платформой, а не прочтение человеком.
Превью картинки/видео ограничено по высоте; картинка открывается в полном размере.
Компактный аудиоплеер поддерживает паузу, перемотку и скачивание.

- По умолчанию показаны все обращения, включая закрытые. Доступны фильтры:
  нужен ответ, открытые, закрытые, мои и все обращения; выбранный фильтр сохраняется в URL.
  Поиск — имя, username или MAX ID.
- «Взять в работу» назначает текущего оператора. Закрытое обращение можно открыть вручную;
  новое входящее открывает его автоматически. Несовместимые изменения двух операторов дают конфликт и обновление данных.
- Непрочитанные персональны. Счётчик в меню показывает общую очередь, требующую ответа.
- Текст и вложения можно отправлять отдельно. Enter отправляет ответ, Shift+Enter переносит строку.
- Картинки открываются в полном размере; у видео и аудио есть плеер и перемотка.
  Запись голоса начинается после нажатия и разрешения микрофона; запись можно прослушать,
  удалить и затем прикрепить. Отмена/уход со страницы останавливает микрофон.
- Черновики отдельных диалогов хранятся в памяти вкладки. После перезагрузки они исчезают;
  в localStorage переписка не сохраняется. После ошибки HTTP текст и ключ запроса остаются.

MAX API отправляет голос оператора как `audio`. Отображение именно нативного голосового
пузыря в клиенте MAX не гарантируется отдельным полем API; это проверяется живым прогоном.
Если браузер не поддерживает запись или воспроизведение, интерфейс объясняет ограничение
и позволяет прикрепить готовый файл/скачать вложение. В Chromium автоматизировано
полное воспроизведение и запись. Windows WebKit проверен с ограничениями его runtime:
без MediaRecorder и доступного нативного декодирования; реальный macOS/iOS Safari требует проверки на устройстве.

## Статусы ответа

| Статус API | В интерфейсе | Что означает |
|---|---|---|
| queued | В очереди | Ответ сохранён, задание ждёт обработки |
| sending | Отправляется | Сохранён intent, worker выполняет отправку |
| sent | Принято MAX | Получен MID от MAX; прочтение человеком не подтверждается |
| failed | Не отправлено | Доказанный отказ; возможен явный повтор |
| unknown | Результат неизвестен | MAX мог получить сообщение; автоматический повтор запрещён |

Для unknown оператор отдельно подтверждает новую отправку с риском дублирования.
Новый ответ получает другой клиентский ключ, вложения копируются в тот же диалог.
Старый неизвестный исход сохраняется в истории. Зависшие sending старше 15 минут
переводятся в unknown. Новый входящий во время отправки остаётся требующим ответа:
ответ покрывает только историю до `reply_to_sequence`.

## Конфигурация

По умолчанию `SUPPORT_MAX_ENABLED=false`. Секреты находятся только в серверном app.env;
не включать их в git, URL интерфейса, логи, скриншоты и диагностический вывод.

| Переменная | Назначение / значение по умолчанию |
|---|---|
| SUPPORT_MAX_ENABLED | Включение поддержки, false |
| SUPPORT_MAX_BOT_TOKEN | Токен отдельного бота |
| SUPPORT_MAX_BOT_USER_ID | Проверенный положительный ID этого бота из GET /me |
| SUPPORT_MAX_WEBHOOK_URL | HTTPS-адрес без path secret, заканчивается `/api/v1/webhooks/max-support` |
| SUPPORT_MAX_WEBHOOK_PATH_SECRET | Отдельный случайный секрет пути, 32–256 символов A–Z/a–z/0–9/_/- |
| SUPPORT_MAX_WEBHOOK_SECRET | Независимый секрет заголовка X-Max-Bot-Api-Secret, 32–256 безопасных символов |
| SUPPORT_MEDIA_HOSTS | Доверенные домены и явные правила поддоменов: `oneme.ru,*.oneme.ru,okcdn.ru,*.okcdn.ru` |
| SUPPORT_IMAGE_MAX_BYTES | 20971520 (20 МиБ) |
| SUPPORT_VIDEO_MAX_BYTES | 262144000 (250 МиБ) |
| SUPPORT_AUDIO_MAX_BYTES | 52428800 (50 МиБ) |
| SUPPORT_FILE_MAX_BYTES | 20971520 (20 МиБ) |
| SUPPORT_VOICE_MAX_SECONDS | 600 — ограничение записи в форме |
| SUPPORT_RETENTION | 4320h — закрытая история хранится 180 дней |
| SUPPORT_FFMPEG_PATH | ffmpeg; ffprobe расположен рядом или доступен через PATH |

API URL, CA и консервативный общий лимит запросов берутся из существующих MAX-настроек.
Per-dialog limiter использует namespace max_support; circuit и outbound history отделены.
При выключении новые секреты не требуются. Test и development без support token используют
fake-провайдер. Реальный worker проверяет ID support-бота, отличие от основного бота и подписки.
Чужую подписку не удаляет и при конфликте останавливает включение с безопасной ошибкой.

Правило `*.oneme.ru` разрешает все уровни поддоменов MAX, включая `i.oneme.ru`,
`iu.oneme.ru`, `fd.oneme.ru` и новые CDN-адреса. Сам `oneme.ru` указан отдельно.
Аналогично разрешено семейство `okcdn.ru`, используемое медиа API MAX. Обычная запись
без `*.` по-прежнему означает только точный hostname. Проверка учитывает границу
домена: `eviloneme.ru` и `oneme.ru.evil.test` не разрешены. Если провайдер перейдёт на
другой корневой домен, его добавляют отдельным явным правилом после проверки.
Скачивание не следует redirect, проверяет DNS/IP и не отправляет bot token в CDN.
Диагностика пишет только UUID вложения, тип, безопасный reason и HTTP status;
подписанные ссылки, имена файлов и токены не журналируются.

## Ограничения медиа и обработка

До пяти изображений/видео в одном ответе. Обычный файл и audio отправляются по одному
с учётом сочетаний, разрешённых MAX. Пределы доступны UI через ответ списка обращений.
Исходящие изображения проверяются по содержимому; аудио нормализуется в MP3, видео — MP4
с H.264/AAC. Оригинал остаётся в приватном storage. Стриминговый WebM без duration
проверяется по длительности полученного файла после конвертации.

В образ добавлены FFmpeg/ffprobe и util-linux. Процесс работает от UID 65532;
конвертация на Linux запускается через prlimit: CPU 120 с, address space 2 ГиБ,
размер файла до 300 МиБ, один поток, общий deadline 3 минуты. Разрешены только локальные
file/pipe-протоколы и ограниченный набор демультиплексоров; сеть конвертеру не нужна.
Ограничение памяти контейнера остаётся дополнительным пределом. Основной образ теперь
использует Debian bookworm-slim с FFmpeg вместо distroless.

Плееры читают приватные файлы через административный endpoint с HTTP Range/206/416.
В S3 используется seekable reader без загрузки видео целиком в память. Обработка идёт
в worker, HTTP только принимает файл в приватное staging. Поддержка использует namespace
`support/`, не рекламную медиатеку; плашка «Реклама» не добавляется.

## HTTP и события

Источник договора — [OpenAPI](../api/openapi.yaml). Операции расположены под
`/api/v1/admin/support`: conversations, история messages, read, update, retry,
attachments и `attachments/{id}/metadata` для опроса готовности staging.
Создание ответа возвращает 202 с UUID и состоянием queued. Поле `client_key` обязательно;
тот же ключ с другим содержимым возвращает 409. ID MAX сериализованы строками.

Маршруты используют обычные Session/CSRF/AdminGate/OpenAPI и IP-политику edge.
Публичен только `POST /api/v1/webhooks/max-support/{secret}` с двумя отдельными секретами.
Тело webhook ограничено 1 МиБ; durable commit предшествует HTTP 200.

SSE v1: `admin.support.changed` содержит UUID диалога, `admin.support.read` — персональную
инвалидацию оператора, `admin.counters.changed` — обновление очередей. Текста, имени,
файлов и provider URL в событиях нет. Изменения отката транзакции в поток не попадают.

## Включение и откат

1. Проверить резервную копию и применить миграции 00112/00113 до новой версии.
2. Выпустить backend и frontend независимо, оставить SUPPORT_MAX_ENABLED=false.
3. Проверить обновлённые Caddy-шаблоны. Dev пропускает только POST на корректный support webhook
   до Basic Auth; callback URL не журналируется. Admin API сохраняет IP-ограничение.
   Для support upload edge допускает 263 MB с multipart, HTTP — 251 МиБ; deadline передачи — 5 минут.
4. Сверить GET /me support-бота и его подписки, не выводя токен/секретный URL.
   Установить секреты/ID/публичный base URL в app.env, затем включить API и worker.
   При активном webhook polling не используется. Если бот уже подключён к другому endpoint,
   сначала разрешить конфликт назначения; worker не удалит подписку автоматически.
5. Пользователь отправляет текст, скриншот, видео и голосовое; оператор читает их и отвечает
   всеми типами, включая запись микрофона. Убедиться в правильном боте, MID и изменении счётчика.
   Отдельно проверить основной бот каналов. Установку и живой прогон фиксировать как эксплуатационный этап.

Откат: выключить поддержку и отключить только принадлежащую этой установке подписку.
Не удалять историю, unknown и jobs; destructive down-миграция для отката приложения не нужна.

Очистка выполняется ежедневно: закрытые диалоги после retention, непривязанное staging
старше суток, служебные входящие payload/ревизии старше 7 дней. Незавершённые
queued/sending/unknown защищают историю от удаления. Файлы удаляются после транзакционного
удаления записей через durable `support_blob_gc`; сбой storage не теряет задание очистки.

## Проверка и диагностика

Backend: `go generate ./internal/apigen`, `sqlc generate`, `go test ./internal/support/...`
с доступным Docker/PostgreSQL, проверки `internal/integration/max` и realtime. В mockapi —
отдельные `go generate ./internal/api` и `go test ./...`. Сценарные данные включают
картинку, воспроизводимые аудио/видео и queued/failed/unknown.

Frontend: `yarn api:types`, `yarn verify`; отдельный слот `yarn slot 7`, затем
`E2E_BASE_URL=http://127.0.0.1:5177 yarn playwright test --config playwright.support.config.ts`.
В Chromium проверяются два окна, черновики, отправка, Range/перемотка, микрофон и размеры
360/390/768/1440; Windows WebKit проверяет UI и объяснения недоступных media runtime-функций.

Если новых обращений нет, проверить доставку webhook, источник max_support и jobs.
Если media failed — проверить allowlist CDN, доступность FFmpeg, лимиты и состояние storage.
Если unknown — не перезапускать отправку вслепую. В логах допустимы только UUID,
операции, статусы, размеры, reason_code; не выводить сырые provider error/body и секреты.
