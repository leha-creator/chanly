# Эксплуатация бэкенда: тестовое окружение и продакшен

Живые проверки внешних контрактов выполняются отдельно от `/readyz`: [доступы и `maxim integration-check`](../../docs/launch/integration-checks.md). Команда разрешена только в изолированном development/staging, использует отдельный тестовый канал и не подтверждает весь контракт одним успешным preflight.

Руководство для дежурного и того, кто готовит сервер. Требования, по которым всё сделано, — [07 §8](../../docs/07-non-functional.md#8-размещение-и-эксплуатация). Заглушка снята с автодеплоя; её историческое устройство — [deploy/README.md](../README.md).

Пометка **«действие человека»** — шаг, который нельзя сделать из репозитория: доступы, договоры, решения, подписи.

## Окружения

| | Тестовое (`staging`) | Продакшен (`production`) |
|---|---|---|
| Каталог на сервере | `/opt/maxim-staging` | `/opt/maxim-production` |
| Проект compose | `maxim-staging` | `maxim-production` |
| `APP_ENV` | `development` | `production` |
| MAX | пусто `MAX_BOT_TOKEN` — подделка; токен тестового бота — тестовый канал | боевой бот |
| Яндекс ОРД | пусто `ORD_OAUTH_TOKEN` — подделка; токен кабинета `ord-prestable` — тестовый контур | `https://ord.yandex.net` |
| Банк | подделки нет: файл выписки делает `maxim dev statement`, загружает `maxim admin money statement import` | выписки банка платформы |
| Почта | Mailpit (профиль `mailpit`, интерфейс на `127.0.0.1:8025` сервера) или SMTP провайдера | SMTP провайдера |
| Рокет Ворк | `ROCKETWORK_MODE=disabled`: подделке нужен общий для `api` и `worker` файл, у стека его нет; подтверждённая тестовая среда (Q-12) — `live` с отдельным target | `disabled` по умолчанию; `live` и допуск workflow настраиваются отдельно |
| Данные | выдуманные; данные продакшена сюда не переносятся | настоящие |

`APP_ENV=test` для серверов не подходит: в нём всегда подделки и хранилище в памяти, оно для тестов Go.

Тестовые данные `maxim dev seed` (README, «Тестовые данные в разработке») — только для `staging`: в продакшене команда отказывает. Запуск — `… run --rm migrate dev seed` при работающем `worker` (как `legal publish` в шаге 6 первого выпуска). На `staging` Рокет Ворк выключен, поэтому сценарии с исполнителем-самозанятым пропускаются. Каналы dev seed выдуманные: с токеном тестового бота MAX `worker` не сможет в них публиковать, тогда запускайте с `--orders=false`.

## Как устроено

```
интернет ─► :443 edge-Caddy (/opt/edge, общий для проектов сервера)
              │  сайт <prefix>.caddy: lb_policy first, проверка /readyz каждые 2 с
              ├─► api-a:8080 ─┐
              └─► api-b:8080 ─┤  (работает одна ячейка; вторая остановлена до следующего выпуска)
                  worker-a/b ─┤
                              ├─► postgres (архив WAL в томе wal-archive)
                  backup ─────┘       │
                    ├─ каждые 30 с: WAL → корзина копий
                    ├─ ночью: физическая и логическая копии, копия объектов, очистка
                    └─ по воскресеньям: проверка восстановления
                  S3 приложения (закрытая и публичная корзины) ─► копия в корзину копий
```

| Файл | Где на сервере | Кто пишет |
|---|---|---|
| [compose.yml](compose.yml), [maxim-app.caddy](maxim-app.caddy), [release.sh](release.sh), [lib.sh](../scripts/lib.sh) | `/opt/maxim-<env>/` | `release.yml` при каждом выпуске |
| `app.env` — переменные бэкенда (шаблон `env/<env>/app.env.example`) | `/opt/maxim-<env>/app.env`, права 600 | человек |
| `stack.env` — переменные compose, пароли PostgreSQL, ключ корзины копий (шаблон `env/<env>/stack.env.example`) | `/opt/maxim-<env>/stack.env`, права 600 | человек |
| `slots.env` — активная ячейка и теги образов | `/opt/maxim-<env>/slots.env` | `release.sh` |
| сайт edge-прокси | `/opt/edge/sites/<EDGE_ALIAS_PREFIX>.caddy` | `release.sh` |

Переменные разделены: `stack.env` с паролем владельца базы и ключом корзины копий не попадает в контейнеры `api` и `worker`. Полный список переменных бэкенда — [.env.example](../../.env.example); проверка шаблонов — `deploy/scripts/check-env.sh` (`--print-missing` — какие значения по умолчанию шаблон не задаёт).

Новые переменные модулей (выплаты, уведомления, споры, API администратора) добавляются в блок `=== Модули в разработке ===` в конце `.env.example` и обоих `app.env.example`, в свой подраздел.

## Первый запуск сервера

1. **Действие человека.** Сервер в России (A-24), Production `chanly.ru` — `194.58.120.196`, Ubuntu 26.04 LTS, чистая установка. Первичный доступ: `ssh root@194.58.120.196` (порт 22, пароль вводится интерактивно). Из полного checkout запустить `bash deploy/app/bootstrap.sh --deploy-pubkey "ssh-ed25519 ... CI" --admin-pubkey "ssh-ed25519 ... admin"`. Скрипт готовит Docker, deploy-пользователя, `/opt/maxim-production`, `/opt/edge` и постоянные тома TLS из `deploy/edge/`. Существующие конфигурации edge не перезаписываются; SSH-пароль не отключается без явного `--harden-ssh` после проверки ключей. Домен окружения — A-запись на сервер.
2. **Действие человека.** Корзины S3 приложения (закрытая, публичная с анонимным чтением объектов) и **отдельная** корзина копий у другого хостера или в другом регионе; ключ приложения — только к корзинам приложения, ключ копий — только к корзине копий. Хранилище секретов (пароли, ключи, токены).
3. `install -d -o deploy -g deploy -m 750 /opt/maxim-<env>`; положить `app.env` и `stack.env` из шаблонов, заменить `CHANGE_ME` (секрет — из хранилища, `CHANGE_ME_BASE64_32B` — `openssl rand -base64 32`), `chmod 600`. Пароль `POSTGRES_APP_PASSWORD` в `stack.env` совпадает с паролем в `DATABASE_URL` в `app.env`, пароль `POSTGRES_PASSWORD` — с паролем в `MIGRATE_DATABASE_URL`.
4. **Действие человека.** GitHub Environment `staging` или `production`: переменные `DEPLOY_HOST`, `DEPLOY_USER`, `DEPLOY_DOMAIN`, секреты `DEPLOY_SSH_KEY`, `DEPLOY_KNOWN_HOSTS`; для автоматического production-выпуска разрешить ветку `master` без обязательного ручного подтверждения. Значения: `DEPLOY_HOST=194.58.120.196`, `DEPLOY_USER=deploy`, `DEPLOY_DOMAIN=chanly.ru`. Ключ CI — отдельный, не root; known_hosts сверить с отпечатком из консоли провайдера. В `stack.env` — `MAXIM_POSTGRES_IMAGE=ghcr.io/leha-creator/maxim-postgres:sha-<full-commit-sha>` из первого запуска `release.yml`.
5. Первый выпуск и каждый последующий: push/merge в `master` запускает **deploy** → **release** после backend/ops-проверок. Пока конфигурация сервера не готова, выпуск завершится ошибкой; после настройки повторить workflow. Ручной **release** остаётся для staging, повторного выпуска и отката. Роли базы создаются при первом запуске PostgreSQL (`deploy/postgres/initdb/10-roles.sh`), миграции применяет `release.sh`.
6. **Действие человека.** Юридические документы: `docker compose --env-file stack.env --env-file slots.env run --rm migrate legal publish …` (тексты — [docs/launch/legal-documents.md](../../docs/launch/legal-documents.md)); роль администратора — `… run --rm migrate admin grant --email <адрес> --role senior`. Сервис `migrate` запускается образом из `MAXIM_TAG_NEW`: перед командой `export MAXIM_TAG_NEW=<активный тег>` (`grep MAXIM_TAG slots.env`).
7. Для продакшена — сертификат Минцифры в образе (`deploy/certs/README.md`, **действие человека**: скачать, сверить отпечаток, закоммитить) и `MAX_CA_CERT_FILE` в `app.env`; в тестовом окружении — только вместе с токеном тестового бота.
8. **Рокет Ворк.** По умолчанию оставить ROCKETWORK_MODE=disabled и ROCKETWORK_WORKFLOW_ENABLED=false. Live-чтение доступно отдельно; автоматизация production требует живой приёмки и ROCKETWORK_PRODUCTION_APPROVED=true. Public API v1 использует Bearer-авторизацию подписки, не HMAC. Онбординг, workflow договор/акт/pay, документы и восстановление реализованы и проверяются локально; работа у провайдера пока не подтверждена. Не настраивать подписку и не пополнять депозит по старой инструкции. Доступы, ротация отдельного токена подписки, блокировки и команды проверки: [матрица интеграций](../../docs/launch/integration-checks.md#рокет-ворк-сверка-openapi--2026-11-09).

Команды compose на сервере всегда с обоими файлами переменных:

```bash
cd /opt/maxim-<env>
dc() { docker compose --env-file stack.env --env-file slots.env --profile slot-a --profile slot-b "$@"; }
dc ps
dc logs --tail=100 backup
```


### Проверки перед открытием production

- Дождаться A-записи `chanly.ru → 194.58.120.196` у публичных DNS; проверить AAAA и делегацию, если менялись NS. Подготовку сервера можно делать заранее. Ошибка TLS или `/readyz` — неуспешный выпуск.
- Заполнить оба env-файла без `CHANGE_ME`; согласовать DOMAIN, PUBLIC_BASE_URL и MAX_WEBHOOK_URL. Адрес кабинета, CDN и отправителя почты задаются отдельно, примеры не являются готовыми production-настройками.
- Указать реальный `EDGE_ADMIN_ALLOW` и CIDR сети edge в `TRUSTED_PROXY_CIDRS`. Не публиковать порт PostgreSQL или административный порт Caddy.
- Для новой БД создать новые пароли и APP_SECRETS_KEY, не импортировать dev seed. Включить отдельное хранилище копий и проверить восстановление в изолированную БД. Проверить роли администратора и опубликованные юридические документы до пользовательского запуска.
- Убедиться, что боевой бот MAX не используется dev-worker, проверить входящие webhook, SMTP, ссылки на объекты и кабинет; проверить `/readyz`, heartbeat worker, резервные копии и запуск после reboot.
- При первом выпуске предыдущей ячейки ещё нет: исправить причину и повторить выпуск. Откат проверяется после второго успешного выпуска; он не откатывает миграции и не восстанавливает старые значения env-файлов. Конфигурацию перед правками сохранять отдельно с правами 600.
- Исторический mockAPI можно остановить после подтверждения его compose-проекта; не удалять тома и чужие сервисы. Автоматика больше не собирает и не публикует `maxim-mockapi`.

## Выпуск и откат

Production выпускается автоматически на каждый push/merge в `master` через **deploy**; PR выполняет только проверки. Workflow **release** также доступен вручную и сначала фиксирует полный SHA, проверяет его через backend/ops, затем собирает `ghcr.io/leha-creator/maxim:sha-<full-commit-sha>` и `maxim-postgres:sha-<full-commit-sha>`, копирует файлы стека и запускает на сервере `release.sh --tag sha-<full-commit-sha>`. Выпуски в одно окружение идут по очереди.

Что делает [release.sh](release.sh):

| Шаг | Что | При ошибке |
|---|---|---|
| `pull` | новый образ | выход, ничего не изменено |
| `config_check` | `maxim config check --for api`, `worker`, `migrate` новым образом и текущим `app.env` | выход, ничего не изменено |
| `base` | `postgres`, `backup` (и `mailpit`, если `SMTP_HOST=mailpit`) — без пересоздания, если не менялись | выход |
| `migrate` | `maxim migrate up` новым образом | выход; старая ячейка работает, миграция совместима с ней |
| `start_new` | `api-<new>`, `worker-<new>`, ожидание `healthy` (`/readyz`) до `--health-timeout` | новая ячейка останавливается, журнал — в выводе; старая работает |
| `edge` | сайт edge-прокси с обеими ячейками, `caddy validate` и `reload` (только если файл изменился) | прежний файл сайта возвращается, новая ячейка останавливается |
| `stop_old` | пауза 3 с, затем плавная остановка старой ячейки: `api` отвечает `503` на `/readyz` ещё `HTTP_SHUTDOWN_DRAIN` (5 с), прокси уводит запросы; `worker` дорабатывает задания до 30 с или возвращает их в очередь | — |
| `slots` | запись `slots.env` | — |

Старая ячейка остаётся остановленной (контейнеры не удаляются). **Откат** — Actions → release с флажком `rollback` или на сервере `./release.sh --rollback`: запускает предыдущую ячейку её образом без миграций и останавливает текущую. Повторный выпуск активного тега без `--reapply` ничего не делает, если API и worker здоровы. CI передаёт `--reapply`: обновлённая конфигурация применяется через новую ячейку даже при том же образе. `--expected-domain` сверяет GitHub DEPLOY_DOMAIN с DOMAIN на сервере до изменений. Одновременно выпуск не запустится (каталог-замок `.release.lock`; если остался после аварии — удалить вручную).

Ключи: `--dry-run` — план без действий, `--skip-pull` — образ уже на сервере, `--no-edge` — не трогать edge-прокси, `--health-timeout SEC`.

Репетиция на своей машине (Docker): `deploy/local/rehearse-release.sh` — выпуск v1, выпуск v2 и откат под запросами каждые 50 мс через свой Caddy на `127.0.0.1:18480`; ждёт ни одного `5xx` и ни одной ошибки соединения. Проект `maxim-rehearsal`, в конце удаляется только он.

### Миграции: расширить → перенести → сузить

Миграция применяется, пока работает старый код, и откат образа не откатывает схему. Поэтому:

- В обычном выпуске — только расширение: новые таблицы, столбцы (с `DEFAULT` или допускающие `NULL`), индексы (`CREATE INDEX CONCURRENTLY` — в отдельной миграции без транзакции), новые значения проверок.
- Удаление и переименование таблиц и столбцов, смена типа, `SET NOT NULL`, `DROP CONSTRAINT` — отдельной миграцией **сжатия** в следующем выпуске, когда ни одна работающая версия (включая ячейку для отката) их не использует. В файле — строка `-- release: contract`.
- Существующие миграции не меняются.

`deploy/scripts/check-migrations.sh [<base-ref>]` проверяет это для новых файлов `migrations/*.sql` (в CI — на каждом PR).

## Резервные копии

Контейнер `backup` (образ `maxim-postgres`, расписание — `BACKUP_*_CRON` в `stack.env`, UTC):

| Что | Когда | Куда (`<корзина копий>/<BACKUP_PREFIX>/…`) | Хранение |
|---|---|---|---|
| WAL | закрытие сегмента не реже раза в минуту (`archive_timeout`), выгрузка каждые 30 с | `db/wal/<сегмент>` | пока нужен самой старой физической копии |
| Физическая копия (`pg_basebackup`) | 00:30 | `db/base/<время>/base.tar.gz`, `backup_manifest`, `manifest.json` | 8 суток |
| Логическая копия (`pg_dump -Fc`) | 01:00 | `db/dump/ГГГГ/ММ/ДД/maxim-<время>.dump`, `.sha256`, `.json` | 30 суток |
| Объекты корзин приложения | 02:00 (`mc mirror`, без удаления) | `objects/<корзина>/` | версии в корзинах приложения — 30 суток |
| Очистка | 03:00 | — | всегда остаётся хотя бы одна копия каждого вида |
| Проверка восстановления | воскресенье 04:00 | — | — |

Потеря данных при аварии сервера — не больше ≈ 1,5 мин (цель 07 §8 — 5 мин). Сбой любого задания пишет `level=error` в журнал и письмо на `ALERT_EMAILS` (не чаще раза в час на вид); контейнер становится `unhealthy`, если WAL не выгружался 5 минут или логической копии больше `BACKUP_MAX_AGE_HOURS` (26 ч).

Состояние и журналы:

```bash
dc exec backup sh -c 'cat /var/lib/backup-state/*.json'
dc logs --no-log-prefix backup | jq -c 'select(.level == "error")'
dc exec backup /usr/local/bin/backup-dump.sh        # внеочередная логическая копия
```

### Проверка восстановления

`restore-check.sh` (по расписанию и вручную `dc exec backup /usr/local/bin/restore-check.sh [--key db/dump/…/maxim-<время>]`): скачивает логическую копию, сверяет `sha256`, поднимает временный кластер PostgreSQL в томе `backup-tmp` того же сервера, восстанавливает и проверяет: возраст копии, версию миграций, наличие таблиц (в том числе выплат `payout` и `rocketwork_contractor`), сходимость журнала проводок (те же запросы, что задание `check_ledger_balance`), наличие в копии объектов до 50 файлов медиатеки. Итог — строка `restore_check_result` с длительностью восстановления; кластер удаляется. Данные не покидают сервер.

### Восстановление логической копии

Когда рабочая база потеряна или испорчена, а точный момент не важен (иначе — восстановление на момент времени ниже).

1. `dc stop api-a api-b worker-a worker-b` — приложение остановлено.
2. Скачать копию и сверить контрольную сумму:
   ```bash
   key=db/dump/ГГГГ/ММ/ДД/maxim-<время>
   dc exec -u postgres backup bash -c '
     . /usr/local/bin/backup-lib.sh; mc_setup
     m cp "$(backup_root)/'"$key"'.dump" /var/lib/backup-tmp/restore.dump
     m cat "$(backup_root)/'"$key"'.dump.sha256"; sha256sum /var/lib/backup-tmp/restore.dump'
   ```
3. Пересоздать базу и восстановить владельцем схемы (`POSTGRES_USER`, по умолчанию `maxim`):
   ```bash
   dc exec -T postgres dropdb -U maxim maxim && dc exec -T postgres createdb -U maxim maxim
   dc exec -T backup cat /var/lib/backup-tmp/restore.dump \
     | dc exec -T postgres pg_restore -U maxim -d maxim --no-owner --exit-on-error
   dc exec backup rm /var/lib/backup-tmp/restore.dump
   ```
   Права роли приложения восстанавливаются из копии (они в ней как `GRANT`).
4. Запустить активную ячейку (`ACTIVE_SLOT` в `slots.env`): `dc up -d --no-deps api-<ячейка> worker-<ячейка>`. Если копия старше текущей схемы, сначала `release.sh` того же тега применит недостающие миграции: выпуск активного тега пропускается, поэтому — `export MAXIM_TAG_NEW=<тег>; dc run --rm migrate`.

### Восстановление на момент времени (в пределах 7 суток)

```bash
dc stop api-a api-b worker-a worker-b
dc exec backup /usr/local/bin/restore-pitr.sh --target-time "2026-10-24 12:00:00" \
  --pgdata /var/lib/backup-tmp/pitr/data           # UTC; --base <время> — конкретная копия
```

Скрипт берёт последнюю физическую копию, начатую раньше цели, применяет WAL из корзины до цели и останавливает сервер. Готовый каталог становится новым PGDATA: остановить `postgres`, сохранить старый том (`docker volume` — не удалять до конца разбора), перенести каталог в том `pgdata`, запустить `postgres`, проверить данные, затем запустить ячейку `release.sh --rollback`/выпуском. В восстановленном кластере `archive_mode` выключен — включить, вернув `command` из compose (перезапуск `postgres`).

Репетиция всего цикла на своей машине: `deploy/local/rehearse-backup.sh` — физическая копия, WAL, логическая копия, копия объектов, `restore-check`, восстановление на момент T (строки до T есть, после — нет) и отказ при испорченной контрольной сумме. Проект `maxim-rehearsal-backup`.

### Квартальная проверка (07 §8)

**Действие человека.** Раз в квартал: `restore-pitr.sh` на момент «вчера, 12:00 МСК» и `restore-check.sh` по последней копии; записать в протокол дату, ключи копий, длительность восстановления (цель — не больше 4 ч), найденные расхождения, подпись ответственного. Где именно делать проверку продакшена — открытый вопрос: 07 §8 говорит «на тестовом окружении», но данные продакшена туда не переносятся; по умолчанию проверка идёт временным кластером на сервере продакшена ([docs/launch/README.md](../../docs/launch/README.md), открытые вопросы).

Для диагностики ОРД на staging оставьте `ORD_REPORT_AUTO_SEND=false`: preflight отклоняет автоматическую отправку. Шаблон явно задаёт `ORD_API_URL=https://ord-prestable.yandex.net` и `ORD_API_VERSION=v8`. Положительный preflight проверяет только конфигурацию; TLS-соединение и API-доступ проверяются отдельно. Порядок получения доступа и текущие блокировки — в [матрице проверок](../../docs/launch/integration-checks.md).

Для проверки чтения sandbox через настоящий адаптер используйте `maxim integration-check --system ord --scenario inspect --execute` с выделенной БД и миграциями. Сценарий не требует реквизитов и ККТУ, не создаёт объектов ОРД и не подтверждает права записи. Параметры, локальный стенд и результаты — в [инструкции проверки ОРД](../../docs/launch/integration-checks.md#штатный-сценарий-чтения-орд).

## API администратора и отчётность ОРД

**Доступ.** Сайт edge отвечает `403` на `/api/v1/admin*` всем, кроме адресов `EDGE_ADMIN_ALLOW` из `stack.env` (CIDR через пробел; `release.sh` подставляет их в сайт и без значения не выпускает). **Действие человека:** до первого выпуска вписать адреса VPN или офиса команды; смена адресов — новый выпуск (`release.sh --tag <активный тег>`) или правка сайта в `/opt/edge/sites/` с `caddy validate` и `reload`. Роль (`moderator`, `senior`) проверяет `api`; выдаёт — `admin grant`.

**Порядок дежурного** — [docs/launch/pilot-plan.md](../../docs/launch/pilot-plan.md#ежедневный-порядок-дежурного): подтверждения денежных операций и ежемесячная отчётность ОРД (1–5-е число отправка, с 20-го оповещение `ord_report_overdue`).

Команды на сервере (`dc run --rm migrate admin …`, как выше):

| Команда | Роль | Что делает |
|---|---|---|
| `admin ord report show --period ГГГГ-ММ` | любая | состояние отчёта месяца: строки статистики, акты, ждут отправки, ошибки |
| `admin ord report build --period … --reason … --email <senior>` | senior | сформировать заново (после решения спора); ничего не отправляет |
| `admin ord report send --period … --reason … --email <senior>` | senior | поставить в очередь отправки строки и акты в `pending` и `error` |
| `admin pd export --email <субъект> --operator-email <senior>` | senior | данные субъекта ПДн в JSON (stdout) для ответа на запрос доступа |
| `admin pd anonymize --email <субъект> --reason … --operator-email <senior>` | senior | обезличить субъекта по [docs/launch/personal-data.md](../../docs/launch/personal-data.md#запросы-субъекта) |

Выгрузку ПДн не сохранять в файл на сервере: вывод команды передать субъекту защищённым каналом (**действие человека**). Обе команды пишутся в `audit_log`; почта субъекта в журнал приложения не попадает.

## Типовые сбои

| Признак | Что делать |
|---|---|
| `backup` `unhealthy`, в журнале `wal_upload_failed` | Проверить доступ к корзине копий (`dc exec -u postgres backup bash -c '. /usr/local/bin/backup-lib.sh; mc_setup; m ls $(backup_root)/'`). Пока S3 недоступен, WAL копится в томе `wal-archive` — следить за диском (`df -h`, `du -sh` тома). После восстановления доступа выгрузка догонит сама |
| `dump_size_mismatch`, `dump_failed` | Повторить `backup-dump.sh` вручную; если повторяется — место в `backup-tmp`, доступ роли `maxim_backup` |
| `restore_check_result` `ok:false` | Смотреть шаг (`step`): `checksum` — копия повреждена, сделать новую; `ledger` — расхождение журнала проводок есть и в рабочей базе (задание `check_ledger_balance`), разбирать как инцидент денег; `objects` — копия объектов отстаёт или файл пропал |
| Диск заполняется | `docker system df`; старые образы — `docker image prune -af --filter until=72h`; том `wal-archive` растёт — S3 недоступен (см. выше); не удалять `pgdata` и `wal-archive` |
| S3 приложения недоступен | `api` отвечает на загрузку медиатеки ошибкой, публикация с изображениями откладывается повторами заданий; восстановить доступ, при потере корзины — объекты из `objects/<корзина>/` копии (`mc mirror` обратно) |
| Выпуск упал на `start_new` | Журнал новой ячейки — в выводе `release.sh`; старая ячейка работает. Исправить и выпустить снова |
| Выпуск завис, `.release.lock` | Убедиться, что `release.sh` не работает (`pgrep -f release.sh`), удалить каталог `/opt/maxim-<env>/.release.lock` |
| Обновление образа PostgreSQL | Только вручную в окно обслуживания: новый `MAXIM_POSTGRES_IMAGE` в `stack.env`, `dc up -d postgres backup` — перезапуск базы (короткий простой). Смена основной версии PostgreSQL — через логическую копию |

## Переход на управляемую PostgreSQL

Если у хостера появится управляемая PostgreSQL в России: сервис `postgres` и задания физической копии и WAL не нужны (копии и восстановление на момент — у провайдера, проверить, что это 7 суток и в России). `DATABASE_URL` и `MIGRATE_DATABASE_URL` — на управляемую базу; роли — по `deploy/postgres/initdb/10-roles.sh` вручную. Контейнер `backup` остаётся для логической копии в свою корзину, копии объектов и еженедельной `restore-check.sh` (`PGHOST` — адрес управляемой базы).

Команды и разбор конфликтов: [Т-Банк](../../docs/launch/integration-checks.md#т-банк--автоматическое-пополнение). Сам факт локальных тестов не разрешает production-синхронизацию.

Сам HTTP 200 не означает полный импорт: проверенная выдача возвращает повторный cursor и собственный перевод вне периода; read/sync корректно остаются незавершёнными. ## Ограниченные реальные пополнения на dev (Т-Банк)

Реальные пополнения на dev включаются флагом `TBANK_DEV_REAL_ENABLED=true` и отдельным кодом назначения `TBANK_DEV_PAYMENT_CODE`. `TBANK_ACCESS_MODE=controlled` выбирает dev-режим зачисления. Нет ограничения одной организацией, срока допуска, лимита одного платежа или суммарного бюджета. Обычные проверки суммы, плательщика, счёта и идемпотентность сохраняются. Т-Банк только читает выписку и не отправляет платежей; права Рокет Ворк независимы.

В `/opt/maxim-dev/app.env` изменить существующие ключи без дубликатов:

```dotenv
APP_ENV=development
TBANK_MODE=live
TBANK_API_URL=https://business.tbank.ru/openapi
TBANK_TOKEN=READ_ONLY_TOKEN_FROM_SECRET_STORAGE
TBANK_CA_CERT_FILE=/etc/maxim/certs/russian_trusted_root_ca.crt
TBANK_IMPORT_FROM=AGREED_RECENT_UTC_RFC3339
TBANK_ACCESS_MODE=controlled
TBANK_DEV_REAL_ENABLED=true
TBANK_DEV_PAYMENT_CODE=CHANLY-DEV
TBANK_PRODUCTION_APPROVED=false
```

Код — 3–48 латинских букв, цифр, дефисов или подчёркиваний; PDF печатает `DEV-TBANK-CHANLY-DEV`. Выбрать отдельный код этого dev-стенда. Проверка без учёта регистра, целым токеном: похожий код с другим окончанием не подходит. Старые `TBANK_CONTROLLED_*` больше не используются, удалить их из app.env. Таблицы бюджета миграции 00101 сохранены как история; новые зачисления их не используют. Миграции не откатывать.

Заполнить настоящие реквизиты платформы (`ORD_PLATFORM_INN`, `ORD_PLATFORM_NAME`, `PLATFORM_*`) и реквизиты плательщиков. Проверить конфигурацию и пересоздать активные api/worker, чтобы загрузить env. Наличие токена само по себе ничего не включает; шаблоны остаются disabled/readonly/false.

В этом dev-режиме любая организация может выставить новый счёт через `POST /invoices` от **1 ₽** до обычного максимума. В остальных режимах минимум **1 000 ₽**. PDF содержит полное назначение с номером `MX-…` и dev-кодом — при оплате скопировать целиком. Без кода или с другим кодом операция остаётся unmatched без deposit. Ручной match и файловый импорт в controlled проверяют тот же флаг и код. Для автоматического зачисления также обязательно обычное сопоставление плательщика и счёта.

Перевод выполняет сам плательщик. Приложение зачисляет поступление один раз: повтор API/файла и рестарт не повторяют deposit или уведомление. Проверка: баланс вырос на сумму, invoice paid, одно balance.deposited. Собственные переводы платформы исключаются. Frontend отсутствует в репозитории; если он фиксирует минимум 1 000 ₽, потребуется учесть dev-минимум API.

Отключение: `TBANK_MODE=disabled` и пересоздание api/worker. Для ручного чтения реальной выписки без зачислений — live/readonly с `TBANK_DEV_REAL_ENABLED=true`. При выключенном флаге live с реальным endpoint отклоняется конфигурацией. Повторное включение допускает прежний код; после смены кода нужны новые счета с новым назначением.

Production automation требует отдельного `TBANK_PRODUCTION_APPROVED=true`, dev-флаг не включает его. Диагностический CLI по-прежнему требует `--target production` и выделенной tbank_check БД; обычный worker использует dev-БД. Секреты не хранить в git. Приложение не ограничивает и не отменяет фактический перевод в банке.

Выставление счёта через T-API и возврат к прежнему PDF:
[BILLING_INVOICE_PROVIDER](TBANK-INVOICES.md). По умолчанию остаётся `local`.

## Изолированные проверки RocketWork на основном аккаунте

Обычные dev API/worker работают через fake/disabled. Основной токен, `ROCKETWORK_CONTROL_DATABASE_URL`, `ROCKETWORK_POLICY_DATABASE_URL` и `ROCKETWORK_CHECK_ARMING_ID` не передаются им, PR CI или dev workspace. Название APP_ENV само по себе не является границей доверия. При прежнем раскрытии токена владелец меняет его до активации runner и удаляет старые копии; этот workflow не выполняет ротацию автоматически.

Профиль `rocketwork-ops` содержит отдельные `rocketwork-runner` и `rocketwork-policy`. Они не наследуют app.env, не стартуют workers, не публикуют HTTP и монтируют только приватные входные JSON из `./rocketwork-input` в режиме чтения. Образ — проверенный выпуск приложения; произвольный код, dev-каталоги и Docker socket не монтируются. Доступ к Docker/ops-хосту ограничен операторами.

1. На доверенной БД отдельно создать роли без memberships по `deploy/postgres/rocketwork-roles.sql`. Не давать эти credentials деву; сетевой доступ — только production и ops-хост. Для миграции задать `DB_ROCKETWORK_POLICY_ROLE=maxim_rw_policy` и `DB_ROCKETWORK_RUNNER_ROLE=maxim_rw_runner` до первого применения миграций контроля. Имена ролей не являются паролями. Миграция 26 помечена contract: все старые экземпляры приложения должны быть выведены перед активацией диагностики с новым видом ledger.
2. Создать на ops-хосте файлы `rocketwork-policy.env` и `rocketwork-runner.env` из шаблонов нужного окружения, с правами 600. В первом — только policy-DSN и внешний arming ID, во втором — runner-DSN, основной RW-токен, origin/target и тот же arming ID. Токен не передаётся владельцу политики, policy-DSN не передаётся runner. Шаблоны не содержат действующих разрешений.
3. Проверить `maxim rocketwork-check fingerprint --manifest /run/rocketwork-input/manifest.json` без сети; владелец отдельно проверяет получателя, реальные договорные условия, допустимую сумму и комиссию. `configure-account --policy ... --alias ...` задаёт общий лимит физического аккаунта; новая alias/grant не создаёт второй бюджет. `issue --policy ... --grant UUID` выдаёт immutable допуск к точным RunID/ManifestHash, а не ко всему аккаунту.
4. Runner выполняет `prepare --manifest ...`, затем `inspect --run UUID` и `status --run UUID`. Перед фактическими записями требуется конкретное разрешение владельца; после него владелец выполняет `arm --account CANONICAL_ID`. Каждый `execute`/`resume` выполняет не больше одного шага. Пример запуска контейнера с проверенным тегом образа: `MAXIM_TAG_NEW=APPROVED_SHA docker compose --env-file stack.env --env-file slots.env --profile rocketwork-ops run --rm rocketwork-runner rocketwork-check status --run UUID`.
5. `revoke --grant UUID` отзывает допуск, `kill --account CANONICAL_ID` запрещает новые записи всего диагностического аккаунта. Уже созданные intent и резервы сохраняются; `inspect`/`reconcile` работают без нового write. Реальная production automation имеет отдельную capability и не включается ради диагностики.

### Backup и восстановление контрольного журнала

Таблицы `rw_check_*`, diagnostic ledger и audit сохраняются вместе с доверенной production-БД. Не включать их в пересоздаваемую dev-БД, не чистить при рестарте и не восстанавливать выборочно ledger отдельно от резервов. Неопределённая операция удерживает номинал и максимальную комиссию через полночь, отзыв допуска и перезапуск. Дневной финансовый расход относится к UTC-дню контрольного settlement; дата резервирования используется отдельно для числа новых операций.

До любого restore остановить runner и отозвать операторский доступ к записям. **Вне восстанавливаемой БД** удалить или сменить `ROCKETWORK_CHECK_ARMING_ID` в защищённой конфигурации. Старые grants из backup не совпадут с новым ID и не разрешат writes. Восстановить журнал с ledger, запускать только `inspect`, `status`, `reconcile`, сверить внешние задачи/комиссии/депозит, затем выдать новый конкретный допуск с новым arming ID. Для незавершённого run сохранить прежние RunID, ManifestHash, номинал и fee ceiling, выполнить владельцем `reauthorize --run UUID --grant NEW_GRANT_UUID` и только затем осознанно включить `arm`. Старый run/intent не сбрасывается в prepared.

Epoch в той же БД не защищает от её отката. Произвольный DBA-restore без этой процедуры автоматически не обнаруживается; владелец сырого токена или администратор доверенного хоста также находится за пределами прикладной защиты. После fee overrun учитывается полный расход и блокируются новые записи; локальный резерв не ограничивает тариф провайдера извне.
