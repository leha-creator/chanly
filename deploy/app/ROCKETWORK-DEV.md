# Проверка RocketWork через интерфейс dev

Production сохраняет автоматическую выплату после приёмки. На dev обычные
выплаты работают через fake; небольшая реальная проверка учитывается отдельно.
Результат диагностики не переводит размещение в P-16 и не погашает выплату блогеру.

## Один раз на сервере

Из checkout на dev-хосте от root:

```sh
python3 deploy/app/setup-rocketwork-control.py --image VERIFIED_APPLICATION_IMAGE
```

Скрипт допускает только стек `maxim-dev` с `APP_ENV=development`. Он создаёт
`maxim_rw_control` в dev PostgreSQL, закрывает CONNECT для PUBLIC, создаёт
изолированные `maxim_rw_runner` и `maxim_rw_policy`, применяет миграции с
неиспользуемой NOLOGIN-ролью `maxim_rw_journal_app` и выдаёт узкие права.
Повторный запуск сохраняет журнал и пароли. Обычная роль `maxim_app` не получает
доступ к этой БД. Секреты лежат на сервере в приватных файлах; в stdout их нет.

Права можно выдать и после уже применённых миграций:
`psql -v app_role=ISOLATED_JOURNAL_APP_ROLE -f deploy/postgres/rocketwork-grants.sql`.
Откатывать миграции или очищать контрольные таблицы для этого нельзя.

БД находится вне обычной dev-БД, но в том же PostgreSQL/pgdata. Сброс
прикладной БД не сбрасывает журнал. Удаление всего pgdata удалит обе БД.
Физическая копия кластера включает журнал; логический dump только `maxim`
его не включает. Для логического восстановления нужен отдельный dump
`maxim_rw_control`. Файлы credentials/arming сохраняются отдельно от dump.
После восстановления используется процедура нового arming ID из основного
руководства; старый допуск не считается новым разрешением.

## Установить конкретный допуск

Оператор задаёт существующего разрешённого исполнителя, канонический аккаунт,
alias, точную сумму, условия договора и последовательность действий в приватном
manifest. Поля `version`, `purpose`, `run_id`, `grant_id`, `terms.ExternalID`
команда `approve-ui` заполнит сама. Хеш вручную вычислять не нужно.

Отдельный приватный файл лимитов содержит `Version`, явно заданный
`MaxCommission` (включая явный 0), `TotalBudget`, `DailyBudget`,
`DailyOperations`, `NotBefore`, `ExpiresAt`. Все денежные значения — копейки;
сумма берётся из `terms.AmountKopecks`, получатель — из manifest. Значений
по умолчанию для денег нет.

```sh
maxim rocketwork-check approve-ui --manifest private/manifest.json --policy private/limits.json
```

Команда запускается только с policy-DSN и внешним arming ID. Она создаёт
grant и неизменяемый подготовленный прогон, возвращает `run_id`, не обращается
к провайдеру. Основной токен ей не нужен. Оператор проверяет выключатель
аккаунта и при необходимости выполняет `arm --account CANONICAL_ID`.

В `rocketwork-runner.env` оператор устанавливает основной RW-токен,
`ROCKETWORK_CHECK_RUN_ID` из результата, случайный
`ROCKETWORK_CHECK_UI_TOKEN` длиной не менее 32 символов. Control-DSN и arming ID
уже подготовлены установщиком. Policy-DSN в этот файл не попадает.

В обычном dev `app.env`:

```dotenv
ROCKETWORK_CHECK_GATEWAY_URL=http://rocketwork-check-ui:8082
ROCKETWORK_CHECK_GATEWAY_TOKEN=SAME_NARROW_UI_TOKEN
```

Это право запустить только установленный прогон. Основной RW-токен, control-DSN,
policy-DSN и arming ID в обычном app.env запрещены. Режим выплат остаётся fake.

Запустить `rocketwork-check-ui` с профилем `rocketwork-ui` и проверенным тегом
`MAXIM_TAG_NEW`, затем выпустить API с обновлённым app.env штатным release.sh.
Сервис не публикует порт наружу, не наследует app.env и не получает Docker socket.
Его запуск без конкретного подготовленного прогона и секретов отклоняется.

## Проверить в браузере

1. Войти на dev старшим администратором и открыть «Выплаты блогерам».
2. В карточке «Проверка Рокет Ворк на dev» проверить получателя, сумму и
   максимальную комиссию. До настройки карточка сообщает, что проверка не настроена.
3. Нажать «Проверить выплату», сверить условия в окне и подтвердить.
4. Дождаться результата. Шаги и сверку продолжает отдельный доверенный сервис;
   браузер только читает состояние. Закрытие вкладки не останавливает сверку.

Повторное нажатие не создаёт новый прогон. При смене установленного `run_id`
старое подтверждение отклоняется через If-Match. После неизвестного исхода
сервис не повторяет POST провайдеру; показывает ожидание сверки. Расхождение
суммы/комиссии показывается отдельно, новые операции заморожены.

Первая версия интерфейса обслуживает один установленный прогон. Новая денежная
проверка требует нового операторского допуска; интерфейс не выпускает grants
и не увеличивает бюджет. Обычные production-выплаты этого допуска не требуют.
